* 这是什么

ebasecamp 把 Docker 环境按 *组 → 配置 → 项目* 组织：

- *组*（group）是可复用的基础组件集合（mysql、redis、应用栈……），是全局第一等对象，不依赖任何项目即可存在；
- *配置*（config）挂在组内，用 =:project= 指向一个项目，并可为该项目覆盖服务字段；
- *项目*（project）是业务工程的容器，提供 =:title=、=:root=、=:shared-network=、=:export-file=。

清单（=groups.el= 与 =projects/*.el=）是唯一事实源，compose 文件只是派生生成物。界面里按服务多选即可批量启动 / 停止 / 重启。

* 安装

#+end_src

** straight.el：开发期（本地仓库）

开发插件本身时用 =:local-repo=，并显式声明 =:files= —— =ebasecamp.el= 在仓库根目录，实现模块在 =lisp/= 下，只拷 =.el= 会漏掉整个 =lisp/=：

#+begin_src elisp
(straight-use-package
 '(ebasecamp :type git
             :local-repo "/home/thomas/WorkSpace/ebasecamp"
             :files ("*.el" "lisp/*.el")))
#+end_src

=:defer t= / =:commands= 之类的延迟加载照常加即可。修改代码后要重建包的 build 目录（=M-x straight-rebuild-package=），否则运行中的 Emacs 仍在用旧副本 —— 现象是 =M-x ebasecamp= 报「命令不存在」。

** straight.el：发布后（远程仓库）

仓库发布后改成 =:repo=，=:files= 保持不变（=:repo= 的值替换成真实的用户/仓库名）：

#+begin_src elisp
(straight-use-package
 '(ebasecamp :type git
             :repo "OWNER/ebasecamp"
             :files ("*.el" "lisp/*.el")))
#+end_src

(add-to-list 'load-path "~/WorkSpace/ebasecamp")

** 第一次使用

#+begin_src text
M-x ebasecamp-create-sample-config   生成示例清单（~/.config/ebasecamp/）
M-x ebasecamp                        打开管理界面
#+end_src

清单已存在时生成命令会拒绝覆盖，确实要覆盖用 =C-u M-x ebasecamp-create-sample-config=。示例清单用的是 *旧写法*（项目侧 =:groups=，见下文），可以正常加载；要体验组内配置写法，按「常见任务」改造即可。

* 清单怎么写

清单目录默认 =ebasecamp-config-directory=（=~/.config/ebasecamp/=）。目录不存在时不会自动创建，=ebasecamp-config-load= 返回 =:bootstrap-needed= t。

| 路径 | 内容 |
|------+------|
| =groups.el= | 服务组定义（可选） |
| =projects/*.el= | 项目定义，按文件名字典序加载 |

** 组定义可以放在 groups.el 或 projects/*.el

加载层按「=groups.el= （存在时）→ =projects/*.el= 字典序」读所有清单文件，组 form 与项目 form 写在哪个文件里都能被读到。所以 *没有 =groups.el= 也能正常工作* —— 导入功能默认就把「组 + 项目」一起写进 =projects/<name>.el= 。界面里的写操作（=S= / =E= / =M= / =X=）按组名跨文件定位组定义的实际位置，改哪儿写哪儿，不会因为缺少 =groups.el= 报错。

要留意 *同一个组名只能在一个文件里定义*：

- 同名组出现在多个文件时，加载层报错「组 X 已定义」，并且 *后加载的那个文件整体回滚* —— 与它同文件的项目定义一起消失，*该项目不会出现在界面中*；先加载的文件照常生效。
- 界面里的写操作一旦发现同名组在多个文件中定义，会直接 *拒绝* 并列出这些文件，要求先清理重复定义（不会静默挑第一个改）。
- 典型来路：用 =X= 新建组会写 =groups.el= ，而旧组可能还在 =projects/*.el= 里；清理时把重复的那份删掉即可。

** groups.el 完整示例

下面两个组覆盖了两种 scope、组内配置、服务字段与跨 scope 依赖，可整段粘贴到 =groups.el=：

#+begin_src elisp
;;; -*- lexical-binding: t; -*-

(ebasecamp-define-group mysql
  :title "MySQL"
  :scope shared
  :services
  ((mysql :image "mysql:8.4"
          :ports ((3306 . 3306))
          :volumes ((:source "mysql-data"
                     :target "/var/lib/mysql"
                     :type volume))
          :environment (("MYSQL_ROOT_PASSWORD"
                         . "${EBASECAMP_MYSQL_ROOT_PASSWORD}"))
          :healthcheck (:test ("CMD" "mysqladmin" "ping")
                        :interval "10s")
          :restart "unless-stopped"))
  :configs
  ((host :project myapp)))

(ebasecamp-define-group app
  :title "应用栈"
  :scope per-project
  :services
  ((api :image "ghcr.io/acme/api:1.2.3"
        :ports ((8080 . 8000))
        :environment (("DATABASE_URL" . "${EBASECAMP_DATABASE_URL}"))
        :depends-on ("mysql"))
   (redis :image "redis:7"))
  :configs
  ((dev :project myapp
        :services ((api :ports ((18080 . 8000))
                        :environment (("LOG_LEVEL" . "debug")))))
   (prod :project other
         :services ((api :ports ((80 . 8000)))))))
#+end_src

读法：

- =mysql= 组是 =shared=，跨项目共用一套容器，只有 *一份* 配置（=host=），它的 =:project myapp= 是「宿主」，只用于渲染与标签归属，不是业务绑定；
- =app= 组是 =per-project=，两份配置分别关联 =myapp= 与 =other=，各项目一套容器；
- =dev= 配置把 =api= 的宿主端口改成 18080 并加了 =LOG_LEVEL=；=prod= 配置改成 80；
- =depends-on ("mysql")= 指向 shared 组的服务，属于 *跨 scope 依赖*：=启动选中= 时会自动先把 shared 批次拉起来。

** 项目文件

=projects/myapp.el=：

#+begin_src elisp
;;; -*- lexical-binding: t; -*-

(ebasecamp-define-project myapp
  :title "示例项目"
  :root "~/Workspace/myapp"
  :shared-network t
  :export-file "deploy/compose.yaml")
#+end_src

=projects/other.el=：

#+begin_src elisp
;;; -*- lexical-binding: t; -*-

(ebasecamp-define-project other
  :title "另一项目"
  :root "~/Workspace/other")
#+end_src

项目关键字：

| 关键字 | 说明 |
|--------+------|
| =:title= | 界面显示名，缺省取项目名 |
| =:root= | 项目根目录。*同时是生成物里相对路径的基准*（顶层 =configs= / =secrets= 的 =file:= 、相对 =volumes= 源、=env_file= —— 经 =--project-directory= 交给 docker），以及导出默认落点、「在项目中打开」的定位依据；详见下节 |
| =:shared-network= | 缺省 =t=：生成物顶层把 =ebasecamp= 声明为 external network |
| =:export-file= | 导出文件名/相对路径（相对 =:root=），缺省 =docker-compose.ebasecamp.yaml= |
| =:groups= | 旧写法的组引用列表，见「旧写法」一节 |

** 项目 =:root= 的作用（v0.5.2 起）

生成物放在缓存目录（per-project 为 =~/.cache/ebasecamp/<project>/compose.yaml= ，shared 为 =<cache>/_shared/compose.yaml=），但 *清单里的相对路径不按生成物解析，而按项目 =:root=* ：

- 受影响的有三类：顶层 =configs= / =secrets= 的 =file:= 、以 =.= 开头的 =volumes= 源（bind 挂载）、=env_file= ；
- 实现方式是派发时注入 *根级 flag* =--project-directory <root>= （必须在子命令之前）：=docker compose -f <cache>/compose.yaml --project-directory <root> -p <name> up -d= ；预校验（=config -q=）与真正的 =up= / =stop= 共用同一基准；
- *副作用*：docker 因此会读取 =<root>/.env= （compose 默认行为），其中的变量参与生成物解析。插件既不读取也不改写该文件；
- shared 生成物用 *触发本次操作的那个项目* 的 =:root= —— shared 配置的 =:project= 只是渲染上下文，不参与推导。

*项目没写 =:root= 会怎样*：不注入该 flag，退回「按生成物所在目录解析」的旧行为（v0.5.1 及之前）。此时顶层 =configs= / =secrets= 的 *相对* =file:= 无法判定 —— 预校验只给一条警告「项目 X 无 :root，无法校验顶层 config `app_cfg' 的 file `./conf/app.conf'」，*不阻塞启动*，成功提示末尾追加「（N 条预校验警告）」；真正的文件缺失要到容器创建阶段才以 =bind source path does not exist= 暴露。*绝对路径* 的 =file:= 不依赖 =:root= ，始终可判定。

** 服务字段表

| 字段 | 形态 | 说明 |
|------+------+------|
| =:image= | 非空字符串（*必填*） | 镜像引用，渲染时原样裸写 |
| =:ports= | =((PUBLISHED . TARGET) ...)= 整数对 | 例如 =(3306 . 3306)= 表示宿主 3306 → 容器 3306 |
| =:volumes= | plist 列表 | =:source= / =:target= / =:type=（=volume= 或 =bind=）/ 可选 =:read-only=；命名卷在生成物里自动改成 =ebasecamp-<scope>-<组>-<source>= |
| =:environment= | 字符串 alist | 值只写 =${VAR}= 引用，插件不插值 |
| =:labels= | 字符串 alist | 用户标签先写，=ebasecamp.*= 五项由插件注入并覆盖同名键 |
| =:command= / =:entrypoint= | 字符串或字符串列表 | 列表渲染为 flow 序列 |
| =:healthcheck= | plist | =:test= / =:interval= / =:timeout= / =:retries= / =:start-period= |
| =:depends-on= | 字符串列表 | 可指向同组、同项目其他组、甚至 shared 组的服务 |
| =:networks= | 字符串列表 | 除 =ebasecamp= 外的额外网络，顶层以空映射声明 |
| =:working-dir= / =:user= / =:restart= | 字符串 | 对应 compose 的 =working_dir= / =user= / =restart= |
| =:extra= | alist | 清单未识别的 compose 字段，导出时原样回写；键名不校验，写错会推迟到 =config -q= 才报错 |

** ${VAR} 约定

- =:environment= / =:labels= 的值里只写引用，例如 =("MYSQL_ROOT_PASSWORD" . "${EBASECAMP_MYSQL_ROOT_PASSWORD}")=；
- 插件不读取、不插值、不打印、不落盘任何密钥值；生成物里同样只有引用，插值由 compose 在运行时完成；
- 相对路径（例如 bind 挂载的 =:source "../api"=）原样保留，不绝对化。

** 配置写法与命名规则

配置写在组的 =:configs= 里，格式 =(配置名 :project 项目名 [:services 覆盖...])=：

| 规则 | 说明 |
|------+------|
| 配置名 | symbol，*组内唯一*；重复会加载报错 |
| =:project= | *必填*，symbol，必须是已定义的项目（项目文件可后加载，存在性在物化阶段校验） |
| =:services= | 可选；格式 =((服务名 :字段 值 ...) ...)=，与组引用的覆盖格式完全一致 |
| =:scope= | *不允许*：配置的 scope 恒等于组定义的 scope |

覆盖合并语义：=environment= / =labels= / =:extra= 按键合并（同名键覆盖、其余保留），=image= / =command= / =entrypoint= / =ports= / =volumes= / =healthcheck= / =depends-on= / =networks= / =working-dir= / =user= / =restart= 整体替换。覆盖组内不存在的服务、或写了未知关键字，都会记入加载错误。

** 旧写法（项目侧 :groups）

v0.1 的写法仍然兼容，视作「匿名配置」，配置名等于组名；引用可以带 =:scope= 与 =:services=：

#+begin_src elisp
(ebasecamp-define-project myapp
  :title "示例项目"
  :groups ((mysql)
           (app :services ((api :ports ((18080 . 8000)))))))
#+end_src

新写法与旧写法可以共存。规则：*同一项目同一组只允许 1 个有效引用*，冲突形态决定结果。

| 形态 | 结果 |
|------+------|
| 项目侧 =:groups= 引用某组 + 组侧 *1 份* =:configs= 指向同一项目同一组 | *以组侧配置为准*（原位接管、位置不变、=:scope= 与 =:services= 取配置值），*不报错* |
| *两份以上* 组侧配置指向同一项目同一组 | 报 =ebasecamp-config-duplicate-group-ref=，消息点名第一份配置 |
| 同一项目在 =:groups= 里重复引用同一组 | 报错（v0.1 静默允许，v0.2 起是错误） |

*** 被问「是否删掉旧 :groups 引用」时怎么选

在界面里 *新建配置*（=X= → 新建配置）或 *改配置关联项目*（=E=）时，如果目标项目仍用旧写法 =:groups= 引用该组，会先问一句：

#+begin_src text
项目 example 的旧写法 :groups 仍引用组 redis；新建配置后该旧引用将被组侧配置
接管。是否同时删掉这条旧引用？
#+end_src

- *答 yes*：在 *同一批写盘事务* 里删掉项目文件里的那条旧引用（若它是 =:groups= 里唯一元素，整个 =:groups= 键一起移除）。此后项目文件只有组侧 =:configs= 一个来源，清单更干净；
- *答 no*：写盘 *仍然成功* —— 旧引用被组侧配置原位接管，界面 / 启停 / 导出读到的都是配置形态；只是下次新建 / 改配置时还会再问一次；
- *意味着什么*：插件不会静默改写你的项目文件。回答 yes 之前，磁盘上不会有任何改动；回答 no 也绝不是失败。

=M=（移动配置）不触发这个询问，也不做旧引用迁移：跨组移动不产生新的「同项目同组」关联，若新位置的组件仍被该项目旧写法引用，走的是「原位接管」。

* 关联项目

关联是 *在组侧声明* 的：给组加一份 =:configs=，=:project= 指向项目即可。加载后插件把配置物化成该项目的组引用，因此界面、启停、导出都自然看到这层关联。

- 一份配置对应一个「组 × 项目」实例，界面右栏给每份配置渲染一段；
- *shared 组的 =:project= 是宿主，不是业务绑定*：它只用于渲染上下文、=ebc-shared= 生成物命名与 =ebasecamp.project= 标签归属。shared 容器全局一套，其他项目通过 external network =ebasecamp= 直接访问，不需要各自再声明一遍；
- 未关联任何项目的组照样出现在左栏（组是全局对象），右栏显示「尚未关联任何项目」与组定义的服务名（只读）。

加载结果可在 batch 下自检（示例见文末「清单自检」）：

#+begin_src elisp
(plist-get (ebasecamp-config-load) :errors)   ; => nil 表示零错误
#+end_src

* 界面操作

=M-x ebasecamp= 打开 =*ebasecamp*= 缓冲区；=M-x ebasecamp-reload= 重新加载清单并刷新。

** 布局

| 区域 | 内容 |
|------+------|
| 顶栏 | =ebasecamp= + 统计（「N 组 · M 配置」）+ =刷新= 按钮 |
| 左栏 | 组树两级：组节点 =MySQL  (2 配置 · 3/4 running)=、配置节点 =dev → 示例项目  (2/2)=；组无配置但有旧写法关联时显示 =redis  (旧 · 1 项目)=，既无配置也无关联时显示 =redis  (未关联)= |
| 右栏 | 选中组的每份配置一段 =etaf-panel=（段头两行 + 服务表）；未选中组时显示「选择左侧的组」 |
| 底栏 | =[I] 导入 compose= / =[o] 导出 compose= / =[D] 销毁环境= |
| 提示区 | =etaf-alert=：成功/信息类 3 秒后自动消失，错误类保留到你手动关闭 |

** 布局与导航

v0.4 起界面是固定在窗口内的三段式（顶栏 / 中间两栏 / 底栏），操作上有六件事值得先知道。

1. *底栏常驻，区域各自滚动*。=导入 compose= / =导出 compose= / =销毁环境= 与提示区固定在窗口底部，任何时候都可见 —— 不再需要把整窗滚到底。配置多时只有你正在看的那个区域在滚（左树滚左树、右栏滚右栏），顶栏与底栏始终不动，整个窗口不再滚动。
2. *=1= / =2= / =3= 跳区域*。分别 *跳到左栏* / 右栏 / 底栏的第一个停靠点，省掉一路 =TAB= 或方向键。焦点进区域后 =TAB= / =S-TAB= 照常在区域内移动。（=1= / =2= / =3= 是 printing key，界面内 evil 的数字前缀因此失效。）
3. *左栏宽度可拖动并记住*。鼠标拖两栏之间的分隔线即可改宽度（也支持键盘拖动），取值范围 0.15–0.55，默认 0.26 —— 比 v0.3 更窄，把宽度让给右栏的服务表格。拖过的宽度写在 =~/.cache/ebasecamp/ui-state.el=（运行时状态缓存，不是清单，随时可删，删了回默认），下次打开界面自动沿用。
4. *主题跟随 Emacs*。界面的前景 / 背景 / 面板 / 边框取自当前 face，状态色（徽标、按钮、警告、勾选）按当前明暗取内置 palette；=M-x load-theme= 切换主题后 *即时* 变色，不用重开界面。想微调可用 =ebasecamp-ui-theme= 按 token 覆盖（默认 =nil= = 完全跟随）。
5. *在项目目录里打开会定位到该项目*。在项目 =:root= 之下的目录里执行 =M-x ebasecamp= ，打开时自动选中该项目 *第一份配置* 所属的组（「第一份」按组定义顺序、组内 =:configs= 顺序取首个 =:project= 命中者；=:root= 嵌套时最长者胜出，路径经 =file-truename= 归一后整段比较、大小写敏感）。当前目录不在任何项目 =:root= 之下、或该项目还没有配置时 —— *不选中任何组*，右栏保持「选择左侧的组」。定位只在打开界面时算一次：=g= / =M-x ebasecamp-ui-refresh= 不会覆盖你手选的组，关闭后重开才重新定位。
6. *vim 手感导航与按字母跳转*。=j= / =k= 上下移动 *焦点*（选中组不变，换组仍是 =n= / =p= ），=h= / =l= 在树内折叠 / 展开；=f= 给组、配置、服务行打上字母提示，按字母直接跳过去。三个键都在根级生效，详见下面「界面操作与键位」的「快速到某个组 / 配置」。

** 左栏：组 → 配置

点组节点选中它，右栏渲染该组全部配置；点配置节点等同于选中它所属的组。默认全部展开，展开状态在刷新后保持。

** 右栏：每份配置一段

段头两行：

1. =配置名 → 项目名= + scope 徽标（=per-project= 蓝 / =shared= 黄）+ =running/total= 徽标；
2. =[s] 启动选中= / =[x] 停止选中= / =[r] 重启选中= 三个按钮（命令执行期间全部禁用）；方括号里的字母就是按下即生效的键，与 =?= 帮助同源。

段体是服务表，列为 *服务 / 镜像 / 状态 / 端口 / 健康*，首列是勾选框。状态文案：=RUNNING= / =STOPPED= / =CREATED= / =PAUSED=；健康文案：=OK= / =BAD= / =STARTING= / =-=；端口列优先显示清单里声明的期望端口。

** 勾选与启停

- 勾选框只写「服务」，不写容器：清单里有定义但没启动的服务同样出现在表里，状态显示 =STOPPED=；
- 勾选状态的 key 是 =组名/服务名=（不含项目名与容器 ID），因此容器重启后选中仍然稳定；同一组的两份配置里若服务同名，勾选状态 *跨段共享*（第一期语义）；
- 点段内按钮只对 *该段自己的项目* 派发，同组多实例不会串段；
- =启动选中= 会先做端口冲突检测：选中集合内宿主端口重复（duplicate）或宿主端口已被占用（busy）会 *拒绝启动* 并给出摘要；探测不可用（unknown，例如权限不足）只提示、不阻塞；
- =停止选中= / =重启选中= 不自动补齐 shared 批次（补齐等于在停止操作里反向启动容器）；
- 命令执行期间会话级 =busy= 为真，段内按钮与重复派发都会被拒绝。

** 底部三个按钮

| 按钮 | 行为 |
|------+------|
| =[I] 导入 compose= | 选文件 → 确认项目名（默认按顶层 =name= / 父目录 / 文件名推断）→ 目标文件已存在时 =y-or-n-p= 确认覆盖 → 落盘 =projects/<name>.el= 并刷新 |
| =[o] 导出 compose= | =completing-read= 选项目 → 渲染 *只含 per-project 组* 的部署用 compose → 写盘前用 =config -q= 校验；覆盖冲突时三选一（换路径 / 覆盖 / 取消） |
| =[D] 销毁环境= | =completing-read= 选项目 → 二次确认框（点名项目，说明不删卷、shared 组不受影响）→ =docker compose down=（不带 =-v=） |

三个按钮都不参与 =busy= 判定（它们不是生命周期动作）；销毁的危险性由二次确认承担。=down= 只对 per-project 项目开放，shared 组没有 =down= 入口。按钮文案前置的 =[I]= / =[o]= / =[D]= 是 *键提示*：按对应键与点按钮走同一条路径，提示与 =?= 帮助同源（段头的 =[s]= / =[x]= / =[r]= 同理）。

** 刷新与轮询

- 界面挂载即启动轮询，间隔 =ebasecamp-status-refresh-interval=（默认 3 秒）；卸载/关闭界面时停止；
- 每次轮询跑一次 =docker ps -a --no-trunc --filter label=ebasecamp.managed=true=，归一后重算整棵树；
- =刷新= 按钮立即采集一次；
- 采集失败（权限、docker 未启动）不会让表格消失：错误留在 =ebasecamp-status-last-error=，界面继续显示上一次成功的数据。

* 界面操作与键位

这一节按操作流程讲界面：怎么开、怎么切组、怎么勾选、怎么起停、怎么改配置、怎么退出。完整键位表见 [[file:../Readme.org][Readme]] 的「界面键位」一节；这里只讲每一步用哪个键、背后发生了什么。

** 打开界面与生成清单

#+begin_src text
M-x ebasecamp-create-sample-config   首次使用：生成示例清单
M-x ebasecamp                        打开管理界面
#+end_src

装了 general 配置时入口在 =thomas-emacs= 侧，是 general 的 =SPC t e e= 绑定，本插件不提供。清单目录为空时界面显示空态页，写出清单目录 =ebasecamp-config-directory= 的位置；生成示例清单后不必重启 Emacs，回到界面按 =g= 即可加载。

** 切换组

左栏是「组 → 配置」两级树。切换当前组有三种方式：

- 用鼠标点组名；
- 按 =n= 或 =p= 在组之间循环，到末尾会回绕；清单里没有组时只提示、不报错；
- 点配置节点，等同于选中它所属的组。

组节点按 =RET= 做的是展开 / 收起，而不是选中。etaf 的树只在叶子上回调选择，因此键盘切换组要用 =n= 与 =p= 两个键；在组节点上按 =RET= 只会展开或收起。

** 快速到某个组 / 配置

组一多，在树里逐个 =n= 翻或一路 =TAB= 就慢了。三条捷径：

- *=f= 按字母跳转*。按 =f= 后界面给 *组 / 配置 / 服务行* 打上字母提示，按那个字母就跳过去（装了 avy 时是单字母提示，跳到的位置与字母标在同一个节点上）。
  - *没装 avy 时自动降级*：弹出 =completing-read= 列表，用名字选（=组名= / =组名/配置名= / =组名/服务名= ），选中后跳到对应位置。功能不依赖 avy。
  - *只跳可见目标*：视口外、未展开组里的配置、未渲染的节点都不在候选里 —— 插件不猜位置，也不会跳到错的条目上。一个可见候选都没有时只在提示区说一句，不移动光标。
  - =f= 只搬焦点，*不改选中组、不切换勾选*：它是浏览动作。跳转期间会暂停 3 秒的状态轮询、跳完恢复，避免刷新重渲染把提示弄乱。
  - 界面内 =f= 是跳转，*不是 evil 的 char motion* —— 根 Host 的键层优先，evil 的 =f= 在界面里收不到键。
- *=j= / =k= 移动焦点*。上下移动焦点（树节点 → 段内按钮 → 服务行 → 勾选框），*选中组不变*；换组仍用 =n= / =p= 。所以 =j= / =k= 可以在服务表里上下移动而不把右栏切走。
- *=h= / =l= 折叠与展开*。在树内 =h= 收起当前组、=l= 展开；已经收起时 =h= / 已经展开时 =l= 会落回焦点左移 / 右移，所以展开态按 =l= 会把焦点外溢到右栏。
- *=1= / =2= / =3= 跳区域*（见上文）：跨区域跳转，与 =j= / =k= 的区域内移动互补。

** 勾选服务

右栏每份配置一段，段体是服务表，首列是勾选框。三种勾选方式等价：

- 按 =t= ：point 落在该行 *任意* 单元格都能切换该行勾选，包括服务名、镜像、状态、端口、健康列；
- 点 =[ ]= 勾选框本身；
- 焦点在勾选框上、或 point 落在 =[ ]= 里时按 =SPC= 或 =RET= ，走 ebox 的「激活当前控件」语义。

勾选状态的 key 是 =组名/服务名= ，不含项目名与容器 ID，因此容器重启后选中仍然稳定。

** 生命周期：启动 / 停止 / 重启

两种入口，行为完全一样：

| 方式 | 操作 |
|------+------|
| 键盘 | point 在段内按 =s= / =x= / =r= ，分别启动、停止、重启该段选中的服务 |
| 鼠标 / 焦点 | 点该段段头的 =启动选中= / =停止选中= / =重启选中= 按钮 |

要点：

- 只对该段自己的项目派发，同组多实例不会串段；
- 没勾选任何服务时会给出「未选中服务」提示，不会静默成功；
- =启动选中= 之前做端口冲突检测：选中集合内宿主端口重复、或宿主端口已被占用，都会 *拒绝启动* 并给出摘要；探测不可用类失败只提示、不阻塞；
- =启动选中= / =重启选中= 派发前还会做一次 *compose 预校验*：本次要用的生成物（shared 与 per-project 都算）逐个 =config -q= ，任一不合法就 *不启动任何容器* 、连 external network 都不建，并在提示区显示 stderr 首行的可读错误（例如 =service "api" refers to undefined config web_cfg: invalid compose project= ）；
- 预校验 *还检查顶层 =configs= / =secrets= 的 =file:= 是否存在*（=config -q= 不覆盖这一层）：按项目 =:root= 逐条判存在性，缺任一条就中止、给出可读错误（见下节「启动失败怎么排查」）；项目没写 =:root= 时只给警告、不阻塞，成功提示末尾追加「（N 条预校验警告）」；
- =停止选中= 与 =D= （销毁环境）不做预校验，生成物暂时不合法时仍可先把服务停掉；
- 命令执行期间段内按钮禁用，会话级 busy 为真，重复派发会被拒绝；
- =停止选中= 与 =重启选中= 不补齐 shared 批次，只有 =启动选中= 才补齐。

** 启动失败怎么排查

| 提示 | 原因 | 处理 |
|------+------+------|
| 顶层 config `xxx` 的 file `./conf/app.conf` 不存在（基准：/home/me/proj） | 清单里顶层 =configs= / =secrets= 声明的相对 =file:= 在项目 =:root= 下找不到；预校验直接中止，*一个容器都没启动* | ① 把文件放到项目 root 下的对应位置；② 或改清单里的相对路径（=:file-configs= / =file-secrets=）；③ 或删掉该顶层 config 定义（服务级对它的引用也要一并去掉）；④ 若路径本就相对别处，改成绝对路径也可 |
| 项目 X 无 :root，无法校验顶层 config `xxx` 的 file `./conf/app.conf` | 项目没写 =:root= ，相对路径无基准。这是 *警告不是失败* | 给项目补 =:root=（推荐）；或在成功提示的「（N 条预校验警告）」背后接受「这条没校验」，注意后续容器创建可能报 =bind source path does not exist= |
| service "xxx" refers to undefined config / secret … | 生成物里服务引用了顶层 config / secret，但顶层段没输出 | 老清单（v0.5.1 之前导入的）重新导入一次原 compose；或手写 =:file-configs= / =:file-secrets= |
| bind source path does not exist: … | 相对 =volumes= 源（以 =.= 开头）在 =:root= 下不存在 —— 这一层 *不做* 预校验，所以推迟到容器创建阶段 | 检查 =:root= 下该路径是否存在；必要时改为绝对路径或命名卷 |
| permission denied while trying to connect to the Docker daemon socket | 当前用户不在 =docker= 组 | 加入 =docker= 组并重新登录（界面里会单独提示这条） |

** 在界面里改配置：=S= / =E= / =M= / =X=

四类改动都能在界面里完成，不必离开 Emacs 去改文件：改服务的 container 字段、改配置的归属、移动配置、增删改配置 / 项目 / 组。四个键的分工：

| 键 | 管什么 |
|----+--------|
| =S= | point 所在 *服务* 的 6 个字段（image / ports / environment / volumes / command / restart） |
| =E= | 当前 *配置* 关联哪个项目 |
| =M= | 把当前 *配置* 移动到其他组的其他项目 |
| =X= | *清单操作菜单*：新建 / 删除配置、项目的新建 / 改 / 删、组的新建 / 改 / 删 |

*** 改端口、环境变量、卷：=S=

以「把 mysql 的宿主端口从 3306 改成 3307，再加一个环境变量」为例：

1. 左栏选中 =MySQL= 组，右栏把 point 放到 =mysql= 那一行（不用先勾选）；
2. 按 =S= ：弹出服务编辑表单，六个字段都填好当前值；
3. =ports= 框里把 =3306:3306= 改成 =3307:3306= ；=environment= 框里加一行 =LOG_LEVEL=debug= ；
4. 点 =保存= 。

三个字段的书写规则（每行一项）：

| 字段 | 写法 | 例子 |
|------+------+------|
| =ports= | =HOST:CONTAINER= 或只写 =CONTAINER= | =3307:3306= |
| =environment= | =KEY=VALUE= ，按首个 = = 切分值 | =LOG_LEVEL=debug= |
| =volumes= | =SRC:DST[:ro]= ；源以 =.= 或 =/= 开头是 bind，否则是命名卷；只写 =DST= 是匿名卷 | =./data:/var/lib/mysql:ro= |

=command= 是 exec 形式、*每行一个参数*（参数里带空格就必须多行）；=restart= 是下拉选择，四个常用值之外的写法选「自定义…」手输。

*写错格式不会写盘*：例如把端口写成 =abc= ，表单内会显示带 *行号* 的错误（=第 1 行：端口必须写成 HOST:CONTAINER 或 CONTAINER（十进制整数），得到 "abc"=），而且 *表单不会关闭* —— 改对再点保存。同样的行号提示也出现在环境变量缺 = =、卷缺冒号、=image= 为空这些情况。

保存成功后界面 *自动重载* 并保持你选中的组，不需要额外操作。只有下面两种情况才需要手动按 =g= ：

- 你在 *外部* 改过清单文件（例如另一个 buffer 里手改 =groups.el= 保存了），此时再保存会被拒绝并提示「文件已被外部修改，先 =g= 重载」—— 这是防止覆盖你的外部改动；
- 界面上显示的状态 / 配置集与磁盘不一致，想强制重读一次。

*** 移动配置到其他组的其他项目：=M=

1. 选中配置所属的组（组内有多份配置时会先让你选配置）；
2. 按 =M= ：先用 =completing-read= 选 *目标组*，再选 *目标项目*；
3. 写盘在一次事务内完成「源组移除 + 目标组追加」，中途不会有「源组已删、目标组没加」的中间态。

两条约束会被拒绝并说明原因：目标组里已有同项目同组之外的冲突（同一项目同一组只允许 1 份配置）、目标组不存在该配置覆盖里引用的服务（此时整笔移动回滚，源配置原样保留）。

*** 新增、删除配置：=X= → 新建配置 / 删除配置

- *新建配置*：输入配置名 → 选关联项目 → 写入当前组的 =:configs= 。配置名组内唯一，冲突时报出来源。
- *删除配置*：选要删的配置 → 确认框 → 从 =:configs= 移除。组内最后一份配置被删掉后 *组仍然保留*（变成「0 配置」的组，左栏照样可见）。

*** 项目与组的新增、改、删（含影响提示）：=X=

=X= 菜单剩下的六项：

| 菜单项 | 收集的输入 | 说明 |
|--------+------------+------|
| 新建项目 | 项目名 / 标题 / 根目录 | 写 =projects/<name>.el= ；文件已存在会被拒绝（改项目请用「改项目」） |
| 改项目 | 项目 / 新标题 / 新根目录 | 只改 =:title= 与 =:root= |
| 删除项目 | 项目 | *有引用保护*：只要有配置的 =:project= 指向该项目就拒绝，并列出「组/配置」清单 |
| 新建组 | 组名 / 标题 / scope | 追加到 =groups.el= ；scope 只能是 =shared= 或 =per-project= |
| 改组 | 组 / 新标题 / 新 scope | 改 scope 的语义影响会由二次确认提示 |
| 删除组 | 组 | *有引用保护*：只要有项目用 v0.1 的 =:groups= 旧写法引用该组就拒绝，并列出项目名 |

删除类操作在动手前会弹确认框。确认框和拒绝消息都围绕同一条原则：

*只删清单，不删容器。* 删除组只删 =groups.el= 里那个组 form，删除项目只删 =projects/<name>.el= 这个文件 —— 已经在跑的 Docker 容器 *不会* 被自动清理。想清理容器请用 =D= （销毁环境，只覆盖 per-project 项目），shared 组容器需要 =docker rm -f= 。

** 手工编辑清单：=e=

界面 buffer 是只读的，手工写只发生在清单文件里：

1. 选中要改的组，按 =e= ：打开 *该组定义所在的清单文件* （=groups.el= 或 =projects/*.el= ，按组名跨文件定位），point 停在 =(ebasecamp-define-group <组名>= 那一行；
2. 按普通 Elisp 编辑，改完保存；
3. 回到界面按 =g= ：重载清单并刷新界面，等价于 =M-x ebasecamp-reload= 。

四条失败路径都会明说原因：没有选中组时提示先在左栏选中；清单目录里一个可编辑清单文件都没有时提示先执行 =M-x ebasecamp-create-sample-config= 生成清单；组名在多个文件里重复定义时提示先清理重复（此时退到 =groups.el= 或第一个项目文件并提示）；文件里找不到该组定义时退到文件头并提示。后两条是降级、不是错误，因为清单可以手写，组也可能在任意 =projects/*.el= 里。这个命令只打开文件，不读取也不打印任何密钥值。

** 退出与帮助

- =q= 关闭界面：卸载 etaf 运行时、停状态轮询、取消提示定时器、销毁会话，而不是 =quit-window= 那样只切走窗口；
- =?= 弹出「快捷键 · 只读」帮助页，列出当前可用键位与中文说明，关闭后界面文本复原。帮助条目按可用视口裁剪，项目多了可能只显示前几条；全量键位看 [[file:../Readme.org][Readme]] 的键位表。

** 为什么按 =i= 不会进 insert

三条机制叠在一起：

1. 界面 buffer 的主模式 =ebasecamp-ui-mode= 派生自 =special-mode= ，并把 =buffer-read-only= 置为 t ，它不接受用户编辑；
2. 界面渲染的根 Host 带 =:key-scope 'local= ，etaf 的键层装在 =emulation-mode-map-alists= 最前面，优先级高于 evil 的 emulation map；
3. local 边界会把 *未绑定的 printing key* 一律吞掉并返回 =ignore= 值。字母 =i= 就被它吃掉。

所以 =i= 在界面里既不会进 insert，也不会有别的反应。它是被键层吃掉，而不是被当成某个命令。技术细节见 [[file:architecture.org][架构]] 的「UI buffer 身份与键位分层」一节。

** 已知边界

| 边界 | 说明 |
|------+------|
| 同组多配置共享选中 key | 勾选 key 是 =组名/服务名= ，不含配置名；同一组的两份配置里服务同名时会一起选中。根因是容器标签没有配置维度（技术债 #10） |
| 段级键跟随焦点 | Tab 定位过某个控件之后，段级键 =s= / =x= / =r= / =a= / =A= 作用于 *焦点所在段* 而不是光标所在段。与段内按钮「按焦点宿主激活」的行为一致 |
| =SPC= 被 ebox 占用 | =SPC= 是 ebox 的激活键，等价于 =RET= ，无法重新绑定；行级勾选用 =t= ，它不会误触按钮 |
| 段外按段级键无提示 | point 在左栏、顶栏时按 =s= 等键被吞掉，没有「请先进入某个段」之类的提示 |
| 服务增删与改名仍不支持 | 表单能改服务字段，但不能新增 / 删除 / 重命名服务：增删会让既有容器变孤儿，改名要迁移容器标签与命名，需先有配置维度（技术债 #16 / #25 / 新增条目）。组服务定义本身仍用 =e= 手写 |
| 组 form 重渲染会规范化排版 | 改配置 / 移动配置会重渲染该组 form，键序固定为 title → scope → services → configs，服务子 form 内部的注释会丢失（组 form 之外的文件内容逐字节保留） |

* 常见任务

** 新增一个组

1. 在 =groups.el= 里加一个 =ebasecamp-define-group=，给出 =:services=（=:title= 可选，缺省取组名）；
2. =M-x ebasecamp-reload=；左栏出现该组（没有配置时右栏显示「尚未关联任何项目」）；
3. 组名只允许 =[a-z0-9_-]+=（小写字母、数字、下划线、连字符）。

#+begin_src elisp
(ebasecamp-define-group cache
  :title "Redis"
  :scope per-project
  :services ((redis :image "redis:7"
                    :ports ((6379 . 6379)))))
#+end_src

** 给组加一份配置

在组的 =:configs= 里追加一项（配置名组内唯一）：

#+begin_src elisp
(ebasecamp-define-group cache
  :title "Redis"
  :scope per-project
  :services ((redis :image "redis:7"
                    :ports ((6379 . 6379))))
  :configs ((dev :project myapp
                 :services ((redis :ports ((6380 . 6379)))))))
#+end_src

=reload= 后左栏该组下多一个 =dev → 示例项目= 节点。

** 把同一组给两个项目（per-project）

两份配置各指向一个项目，配置名必须不同：

#+begin_src elisp
(ebasecamp-define-group app
  :title "应用栈"
  :scope per-project
  :services ((api :image "ghcr.io/acme/api:1.2.3"))
  :configs ((dev  :project myapp :services ((api :ports ((18080 . 8000)))))
            (prod :project other :services ((api :ports ((80 . 8000)))))))
#+end_src

两个项目各有一套独立容器（=ebc-myapp= / =ebc-other=），网络通过 =ebasecamp= 互通。

** shared 组跨项目共用

1. 组声明 =:scope shared=，并只给它 *一份* 配置（=:project= 填任一已定义项目当宿主）：

#+begin_src elisp
(ebasecamp-define-group mysql
  :title "MySQL"
  :scope shared
  :services ((mysql :image "mysql:8.4"))
  :configs ((host :project myapp)))
#+end_src

2. 其他项目 *不需要* 再引用该组：shared 容器全局一套，通过服务名 + external network 访问；
3. 界面里该组只有一段，状态按 =scope + group= 匹配（宿主项目之外的容器也计入）。

** 从已有 compose 导入

#+begin_src text
M-x ebasecamp-import-file        或界面底栏「导入 compose」
#+end_src

导入会用 =docker compose -f <file> config --no-interpolate --no-env-resolution --no-path-resolution --format json= 读取（三个 flag 缺一不可：否则密钥明文展开 / =env_file= 合并 / 相对路径被绝对化），然后落盘成两份定义：

- 组名与项目名相同，都取你确认的名称，服务写进组的 =:services=；
- 同一个组的 =:configs= 写一项 =(组名 :project 项目名)=；
- 项目定义只写 =:title= 与 =:root=，*不必* 写 =:groups= —— 项目侧引用由加载期物化产生。旧写法仍兼容：与组侧 *1 份* 配置指向同一项目同一组时由配置原位接管（不报错），只有 *2 份以上* 组侧配置指过来才报双引用错误。

导入后 =reload=，在左栏选中该组即可看到服务；项目根目录默认取 compose 文件所在目录。

** 顶层 configs / secrets 与「重新导入」

服务引用 compose 顶层声明的 config / secret 时（服务级 =configs: [{source: web_cfg}]= 指向顶层 =configs: {web_cfg: {file: ./web.conf}}= ），导入会把顶层段保留到 *项目定义* 的 =:file-configs= / =:file-secrets= 槽，启动时再渲染回生成物。

*v0.5.1 之前导入的清单必须重新导入一次*：那些清单里没有这两个槽，服务级 =configs:= 引用虽然还在（原样透传），顶层段已丢失，按 =s= 会报 =service "xxx" refers to undefined config= 。修法：

1. 用 =M-x ebasecamp-import-file=（或界面底栏 =导入 compose= ）选 *原来那份 compose* ；
2. 项目名填原来的项目名，覆盖确认时选覆盖；
3. 回界面按 =g= 重载，再按 =s= 即可通过预校验。

*启动时还会核对 =file:= 是否存在*：=s= 的预校验按项目 =:root= 逐条检查顶层 =configs= / =secrets= 声明的 =file:= （=config -q= *不* 校验这一层，缺文件要到容器创建阶段才报），缺失就当场中止并给出可读错误：

#+begin_src text
顶层 config `app_cfg' 的 file `./conf/app.conf' 不存在（基准：/home/me/myapp/conf/app.conf）
#+end_src

因此「导入后文件没放在项目根下」会在第一次按 =s= 就暴露，而不是等到容器创建才炸；处理办法见「启动失败怎么排查」表第一行。

插件 *不会自动改写* 你的清单，也不会自动补顶层段。已知限制：=shared= 生成物（=ebc-shared=）不输出顶层 =configs= / =secrets= 。顶层 config / secret 支持 =file:= / =external= / =name= 与 inline =content:= （含多行字符串，v0.5.4 起以 YAML 块标量保真往返）。

** 部署导出

#+begin_src text
M-x ebasecamp-export-compose     或界面底栏「导出 compose」
#+end_src

导出物与缓存生成物的差异：

| 项 | 缓存生成物 | 导出物 |
|----+------------+--------|
| 组范围 | 按 scope 分批（=ebc-shared= / =ebc-<project>=） | 只含 *per-project* 组 |
| =ebasecamp= external network | 顶层声明 | *不声明*（部署机无需预建网络） |
| 生成头注释 | 无 | 有（来源项目、清单路径、重新生成命令、shared 未包含说明） |
| 位置 | =~/.cache/ebasecamp/...= | =<root>/docker-compose.ebasecamp.yaml= 或 =:export-file= |

写盘是原子的：先写 =.tmp=，用 =docker compose config -q= 校验（退出码 + stderr 双判据），通过才改名到目标文件；失败时目标文件不会出现半成品。shared 组服务不写进导出物 —— 它们由部署环境自行提供。

* 限制与注意事项

| 限制 | 说明 / 规避 |
|------+-------------|
| 同一项目同一组只能 1 份配置 | 容器标签没有配置维度，同名服务会撞。需要「同一组在同一项目两套」时目前无解（记在技术债） |
| shared 组至多 1 份配置且 =:project= 必填 | 多宿主会互相覆盖 =_shared/compose.yaml= 与 =ebc-shared= 容器集合；缺 =:project= 直接加载报错 |
| 旧 =:groups= 写法可用，但同一项目同一组只允许 1 个 *有效* 引用 | 旧写法 + *1 份* 组侧配置指向同一项目同一组 → 组侧配置 *原位接管*（不报错，位置不变）；*2 份以上* 组侧配置指向同项目同组、或 =:groups= 里重复引用同一组 → 报 =ebasecamp-config-duplicate-group-ref=。修法：删掉重复项，差异并入唯一那一项的 =:services=；界面新建 / 改配置时会问你是否顺手删掉旧引用 |
| 旧 =:groups= 关联显示为「旧写法」段 | 组侧没有 =:configs= 的 v0.1 清单：组节点文案为 =MySQL  (旧 · 1 项目)=、右栏段头为 =（旧写法）→ 示例项目=，并在组标题下给迁移提示（服务仍可正常启停，只是没有配置名）。改成组侧 =:configs= 后段头恢复为 =配置名 → 项目=；组既无配置也无关联赛显示 =(未关联)= |
| =env_file= 需重新导入 | 清单形态已由 =((:source PATH :type env))= 改为路径字符串列表（=("./db.env")=）；D4 之前导入的清单继续导出会报 =env_file must be a string= |
| 界面不做服务增删与改名 | 表单能改服务字段（=S=）与配置 / 项目 / 组的增删改（=E= / =M= / =X=），但新增 / 删除 / 重命名 *服务* 仍要手写清单（=e=）：增删会让既有容器变孤儿，改名要迁移容器标签与命名（技术债 #16 / #25） |
| 没有 shared 清理入口 | 插件侧 =down= 只覆盖 per-project；shared 容器需 =docker rm -f=（技术债 #16） |
| =重启选中= 不补齐 shared 批次 | 重启前请确认 shared 服务仍在运行；=depends-on= 里的笔误会被静默剔除（技术债 #14） |
| =:extra= 不做 schema 校验 | 只放合法 compose 字段，否则到 =config -q= 才报错 |
| 跨组同名服务静默保留首个 | compose 生成时同名服务不报错，后一份被丢弃（技术债 #9） |
| 端口冲突只在 =启动选中= 前检测 | 停止 / 重启不做检测；=unknown= 类探测失败不阻塞 |
| =busy= 是会话级 | 多项目并行被收窄为单飞（技术债 #15） |
| 状态最多滞后一个轮询周期 | 默认 3 秒；需要即时值点 =刷新= |
| 名字字符集 | 组名与项目名只允许 =[a-z0-9_-]+=，其余字符在渲染时直接报错 |
| 配置不覆盖 scope | 同一组在不同项目需要不同 scope 时，拆成两个组或改用旧写法的引用级 =:scope= |
| 顶层 =configs= / =secrets= 的 =content= 多值 / 多行 | 已支持（v0.5.4）：=file:= / =external= / =name= 之外，inline =content:= 含多行字符串也保真往返（YAML 块标量，chomping 按末尾换行数取 strip / clip / keep）。判据用 =config --format json= 对比 =content= 字符串 —— =config -q= 只校验语法不校验内容 |
| shared 生成物不含顶层段 | =ebc-shared= 不输出 =configs= / =secrets= ，shared 组服务引用顶层 config / secret 需自行处理 |
| 老清单需重新导入一次 | v0.5.1 之前导入的清单缺 =:file-configs= / =:file-secrets= ，引用顶层 config 的服务启动会报 =refers to undefined config= ；对原 compose 重新导入即可补齐，插件不自动改清单。两点注意：①*重导入会 =--force= 覆盖界面对该项目的编辑*（导入是「按 compose 文件重建项目定义」，不是合并），依赖界面里加过的覆盖 / 端口时必须先备份清单；②inline 多行 =content:= 的顶层 config 已可保真往返，无需改 =file:= 形态；但 v0.5.1 之前导入的清单仍需重导入一次才能补齐 =:file-configs= |
| 同名组只能在一个文件里定义 | 同名组出现在多个文件时加载层报错「组 X 已定义」，*后加载的文件整体回滚* —— 其中项目不会出现在界面；界面写操作遇到同名组直接拒绝并列出文件 |
| 导出的路径基准不由插件改写 | 导出到 *项目 =:root= 之外* 的目录时，导出物里顶层 =configs.file= 的相对路径会失效（导出物的基准是导出目标所在目录）。改法：导出到项目 root 下，或手写绝对路径。v0.5.3 起这种情形会 *提示一次*：「导出目录 … 不是项目 root …：生成物里的相对路径（env_file / bind 挂载）在部署时按导出目录解析，请确认相关文件随生成物一同部署。」提示只提示 —— 不改导出结果、不影响成败，也 *不会* 把校验基准换成项目 root（换基准等于「校验过、部署炸」） |
| 项目 =:root= 可选（留空 = 无根目录项目） | 三条降级：①*界面不按目录定位* —— 站在该项目目录里 =M-x ebasecamp= 不会自动选中它的配置；②*不作路径基准* —— 派发不带 =--project-directory=，相对 =file:= 的预校验 *只给警告*（成功提示末尾「（N 条预校验警告）」），*不是启动失败*，真正的缺失要到容器创建阶段才有 =bind source path does not exist=；③*导出必须显式选路径* —— 无 =:root= 也无 =:export-file= 时交互式弹 =read-file-name=，非交互调用仍报错。界面「改项目」把根目录留空即 *清空* =:root=（会先弹确认，清单里该键真正消失，不会留 =:root nil=） |
| 无 =:root= 但写了 =:export-file= | =:export-file= 是相对路径时按 *=default-directory=（导出调用时的当前目录）* 展开，而不是项目 root —— 这是既有语义（没有 root 就没有别的基准可用），v0.5.3 未改；需要稳定落点时写绝对路径或在界面里当场选 |
| 相对 =volumes= 源不做存在性检查 | 预校验只覆盖顶层 =configs= / =secrets= 的 =file:= ；以 =.= 开头的 bind 源缺失要到容器创建阶段才报 =bind source path does not exist= |
| =M=（移动配置）不迁移旧 =:groups= 引用 | 跨组移动不产生新的「同项目同组」关联，不做迁移；目标项目若仍用旧写法引用该组，由「原位接管」兼容 |
| 预校验警告只显示条数 | 成功提示末尾的「（N 条预校验警告）」只是计数，界面不逐条列出；具体消息在 =ebasecamp-command-run= 返回值的 =:preflight-warnings=（batch 下可自行取） |

* 清单自检

改完清单先做一次零错误检查，再看组与配置是否都读到了：

#+begin_src elisp
(let ((result (ebasecamp-config-load)))
  (list :errors (plist-get result :errors)                 ; => nil
        :groups (mapcar #'ebasecamp-group-name
                        (plist-get result :groups))        ; => (mysql app)
        :configs (mapcar #'car (ebasecamp-model-group-configs 'app))))
                                                                ; => (dev prod)
#+end_src

批量模式（不加载用户 init）下的等价命令，成功时打印 =nil=：

#+begin_src sh
emacs -Q --batch -L . -L lisp \
  -L "$HOME/thomas-emacs/.local/straight/build-31.1/etaf" \
  -L "$HOME/thomas-emacs/.local/straight/build-31.1/etaf-ui" \
  -L "$HOME/thomas-emacs/.local/straight/build-31.1/ebox" \
  -L "$HOME/thomas-emacs/.local/straight/build-31.1/ecss" \
  --eval "(progn (require 'ebasecamp-config) (prin1 (plist-get (ebasecamp-config-load) :errors)))"
#+end_src

清单目录换位置时把 =ebasecamp-config-directory= 一起改掉，或给 =ebasecamp-config-load= 传目录参数。
