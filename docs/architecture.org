* 定位与范围

ebasecamp 是 Emacs 里的 Docker 环境分组管理插件。v0.2 起，模型的中心是 *组*：组是全局第一等对象，不依赖任何项目即可存在；组的每一份 *配置* 关联一个项目，加载期被物化成该项目的组引用。

两条不变式撑起整个架构：

- *清单是唯一事实源*：组与项目以 Elisp 形式保存在 =~/.config/ebasecamp/= （=groups.el= 与 =projects/*.el=）；compose 文件要么是可重建缓存（=~/.cache/ebasecamp/=），要么是用户显式触发的部署导出物。
- *下游只读统一形态*：无论组引用来自旧写法（项目侧 =:groups=）还是新写法（组侧 =:configs= 物化而来），进入渲染 / 命令 / 状态 / 导出层时都是同一个 plist 形态 =(:group SYMBOL :scope SCOPE :service-overrides ALIST)=。

本文档描述 *当前实现* （v0.5.2）；代码是最终依据，文档与代码冲突时以代码为准并回头修文档。数据模型的设计理由见 [[file:adr/0001-architecture.org][ADR-0001]]，compose 映射细节见 [[file:compose-generation.org][compose 生成]]，操作步骤见 [[file:user-guide.org][用户指南]]。

* 分层与依赖方向

依赖方向的文字层级（列表序为从最底层到界面层：上层可依赖下层，下层不得依赖上层）：

1. =model= / =config=
2. =compose= / =import= / =export=
3. =docker=
4. =command= / =status=
5. =data=
6. =ui=

各层职责与禁止事项：

| 层 | 模块 | 职责 | 禁止事项 |
|---+------+------+----------|
| 1 纯数据 | =ebasecamp-model= / =ebasecamp-config= | 三个 struct、字段校验、覆盖合并、清单加载与加载期物化 | 不依赖 etaf / docker；不做 IO（=config= 只读清单文件） |
| 2 渲染映射 | =ebasecamp-compose= / =ebasecamp-import= / =ebasecamp-export= | 清单 → YAML 文本、compose JSON → 清单结构、部署用导出 | 不写注册表、不执行 docker、不解析 YAML |
| 3 进程 | =ebasecamp-docker= | 起进程、捕获 stdout/stderr、解析 =ps= 与 =config=、版本检测 | 不判断业务语义（哪些服务该起、状态如何聚合） |
| 4 语义 | =ebasecamp-command= / =ebasecamp-status= | 生命周期分派、按 scope 拆批、跨 scope 补齐、端口冲突检测、状态归一与聚合 | 不渲染界面；轮询定时器只在 UI 挂载期间运行 |
| 5 装配 | =ebasecamp-data= | 清单 ∪ 状态的纯装配：=project-records=、=group-instances= | 不依赖 UI 框架、不做查询/分页/轮询、不持有全局资源 |
| 6 界面 | =ebasecamp-ui= | etaf 渲染、会话状态（=etaf-ref=）、动作派发、导入导出入口 | 不拼 docker 命令、不直接调 =docker= 层 |

硬约束：

- UI 层只能调用 =command= / =status= / =data= 的公开接口，进程与参数构造只允许出现在 =ebasecamp-docker.el= / =ebasecamp-command.el= （AGENTS.md 禁止行为 1）。
- =model= / =config= 不依赖 etaf，可在 =emacs -Q --batch= 下单独加载与单测。
- =compose= 对 =ebasecamp-model-resolve-services= 返回的浅拷贝 *只读*：=ports= / =volumes= / =environment= / =extra= 的列表结构与组内对象共享，禁止 =setcar= / =plist-put= 就地修改。
- =data= 只读最近一次成功快照（=ebasecamp-status-last-records=），自己不执行 =docker ps=：轮询归 =status=，避免一次刷新跑两次 docker。

* 数据模型

三个 struct 定义在 =ebasecamp-model.el=，字段为：

| struct | 字段 |
|--------+------|
| =ebasecamp-service= | =name= =image= =command= =entrypoint= =environment= =labels= =ports= =volumes= =healthcheck= =depends-on= =networks= =working-dir= =user= =restart= =extra= |
| =ebasecamp-group= | =name= =title= =scope=（=shared= / =per-project=，缺省 =per-project=）、=services=（=ebasecamp-service= 对象列表）、=configs=（=((配置名 . PLIST) ...)=） |
| =ebasecamp-project= | =name= =title= =root= =groups=（归一化组引用 plist 列表）、=shared-network=（缺省 =t=）、=export-file= |

字段约定（校验在 =ebasecamp-model--check-*= 系列里，违反即 signal =ebasecamp-model-error=）：

| 字段 | 允许形态 |
|------+----------|
| =name=（组/项目/服务/配置） | 非 nil symbol |
| =ports= | =((PUBLISHED . TARGET) ...)=，两个整数 |
| =volumes= | plist 列表：=:source= / =:target= / =:type=（=volume= 或 =bind=）/ 可选 =:read-only= |
| =environment= / =labels= | 字符串 alist，值中的 =${VAR}= 原样保留 |
| =depends-on= / =networks= | 字符串列表 |
| =command= / =entrypoint= | 字符串或字符串列表 |
| =working-dir= / =user= / =restart= | 字符串 |
| =healthcheck= | plist 或 nil |
| =extra= | alist，导出时原样回写 |

** 组引用（统一形态）

项目 =groups= 槽的每一项都是：

#+begin_src elisp
(:group mysql :scope shared
 :service-overrides ((mysql :ports ((3307 . 3306))
                             :environment (("LOG_LEVEL" . "debug")))))
#+end_src

- =:group= 是组名 symbol；=:scope= 为 nil 时取组自身声明的 scope（引用级 =:scope= 只影响该项目的解析语义，不修改组对象）。
- =:service-overrides= 是 =((服务名 . 属性 plist) ...)=；覆盖合并语义见 =ebasecamp-model--merge-service=：=environment= / =labels= / =extra= 按键合并，其余字段整体替换。覆盖组内不存在的服务会 signal。
- *这个键名必须是 =:service-overrides=*，写 =:services= 会让下游覆盖静默丢失（不变量 9）。

** 组内配置（新写法）

组的 =configs= 槽形如 =((配置名 . PLIST) ...)=，按定义顺序保存，配置名在组内唯一且必须是 symbol：

#+begin_src elisp
(ebasecamp-define-group app
  :title "应用栈"
  :scope per-project
  :services ((api :image "ghcr.io/acme/api:1.2.3"))
  :configs ((dev  :project myapp :services ((api :ports ((18080 . 8000)))))
            (prod :project other :services ((api :ports ((80 . 8000)))))))
#+end_src

配置只允许两个关键字 =:project=（必填，symbol）与 =:services=（覆盖，格式与组引用的 =:services= 完全一致）。*配置不提供 =:scope=*：配置的 scope 恒等于组定义的 scope（设计决策 D9），因此不存在「配置 scope 与组 scope 不一致」的歧义；同一组在不同项目需要不同 scope 时，要么拆成两个组，要么回到旧写法（项目侧 =:groups= 仍支持引用级 =:scope=）。

* 加载期物化机制

** 为什么要物化

新写法把「组 → 项目」的关联声明在 *组侧* （=:configs=），而渲染、命令、状态、导出五处读取点都按 *项目侧* =project.groups= 工作。若不搬运，这五处都要改写成「先查配置再查项目」，模型变更的复杂度会扩散到每个模块。

物化就是把每份配置转换成 *与 =ebasecamp-model--group-ref-from-spec= 完全同构* 的组引用，=append= 到对应项目的 =groups= 槽末尾。于是下游零改动，读取点保持不变（已核实）：

| 读取点 | 位置 | 读什么 |
|--------+------+--------|
| =ebasecamp-compose--group-refs= → =ebasecamp-compose-render= | =ebasecamp-compose.el= | 项目 =groups= 槽（含 =:scope= 与 =:service-overrides=） |
| =ebasecamp-command--selection= | =ebasecamp-command.el= | 选中 key 解析到引用，再用 =resolve-services= 合并覆盖 |
| =ebasecamp-data-project-records= | =ebasecamp-data.el= | 引用列表 → 服务记录 |
| =ebasecamp-export--per-project-refs= | =ebasecamp-export.el= | 只取 per-project 引用 |
| =ebasecamp-compose--ref-scope= | =ebasecamp-compose.el= | 引用的有效 scope |

** 算法（ebasecamp-model-link-configs）

1. 每个项目的 =groups= 槽先回到「物化前基线」（见幂等）。
2. 逐组逐配置校验，任一命中即记一条错误并 *跳过该配置*，不中断其余项：
   - 配置引用的项目未定义 → =:undefined-project=；
   - 同项目同组已有 *另一份配置* 物化出的引用 → =:duplicate-group= （由旧 =:groups= 提供的引用 *不算冲突*，见下「双簿记」）；
   - shared 组配置份数 > 1 → =:shared-multiple-configs=，*整组跳过*（无法判定哪份生效）；
   - 覆盖了组内不存在的服务 → =:unknown-service=；
   - 覆盖项本身非法 → =:invalid-services=（模型层已校验，此处兜底）。
3. 通过的配置转成引用后：该引用若正由旧 =:groups= 提供且尚未被接管 → *原位替换*（=:group= / =:scope= / =:service-overrides= 取配置值，列表位置不变）；否则 =append= 到项目 =groups= 末尾 —— *旧 =:groups= 引用在前，物化结果按「组定义顺序 → 配置定义顺序」在后*。

** 双簿记：=sources= 与 =legacy= 不可混用

「能否被接管」*不能* 靠比较来源字符串决定（=“旧 :groups”= / =“配置 X”= / 兜底 =“另一份配置”= 三种形态共存）。因此 =ebasecamp-model-link-configs= 内并列维护两个 hash，键都是 =(项目名 . 组名)=：

| 簿记 | 内容 | 用途 |
|------+------+------|
| =sources= | 当前有效引用的 *来源串*（旧 =:groups= / 「配置 <配置名>」/ 兜底「另一份配置」） | *只* 拼进错误消息，任何行为分支都不比较它的值 |
| =legacy= | 值恒为 =t=，标记「该引用当前由旧 =:groups= 提供、可被组侧配置接管」 | 冲突时 *唯一* 的判据 |

流程：步骤 1 回填基线时对每条旧引用 *同时* 写两个 hash；E2 命中「同项目同组已有引用」时先查 =legacy= ——

- 有标记 → 接管、不记错误；随后 =remhash= 该键并把 =sources= 更新为「配置 <名>」。**顺序很重要**：不清标记的话，第二份配置会再接管一次并 *静默丢掉第一份*；
- 无标记 → 报 =:duplicate-group=，来源取 =sources=（nil 时兜底「另一份配置」）。

*原位替换只对 groups 槽里那个列表 cell 做 =setcar=* ，不改 reference plist、也不改基线快照：基线是浅拷贝，改 plist 会污染下次重算的起点从而破坏幂等；改 cell 则既保持「旧引用位置不变」，又让每次重算的结果稳定。配置的定义顺序因此不影响结果。

错误项与 =ebasecamp-config-load= 的 =:errors= 元素同形 =(:file PATH :condition CONDITION-DATA :message STRING)=；模型层不感知文件，=:file= 恒为 nil，由 =ebasecamp-config--link-configs= 统一补填成 =<dir>/groups.el= （配置只能写在 groups.el）。

** 幂等策略（基线快照）

注册表只支持追加，重复调用物化会累积重复引用。因此首次处理某项目时，把它当时的 =groups= 槽浅拷贝进 =ebasecamp-model--legacy-groups= （hash：项目名 → 引用列表）作为基线；此后每次物化都从基线重算、重新追加。于是：

- =link-configs= 连续调用两次结果相同（幂等）；
- 不调用 =link-configs= 时，项目 =groups= 槽保持定义时的原样（v0.1 行为不变，旧写法兼容）；
- =ebasecamp-model-reset= 清空注册表时一并 =clrhash= 基线，保证重新加载不残留。

** 加载顺序（ebasecamp-config-load）

| 步骤 | 动作 | 出错处理 |
|------+------+----------|
| 1 | 清空注册表（=ebasecamp-model-reset=） | — |
| 2 | 加载 =groups.el=，再按文件名字典序加载 =projects/*.el= | 单个文件出错记错误，并用「重置 + 重放已成功文件」丢弃该文件已产生的定义 |
| 3 | =ebasecamp-config--validate-projects=：未定义组、同项目重复引用同组 | 追加错误（定义期） |
| 4 | =ebasecamp-config--link-configs=：物化组内配置 | 追加错误（物化期），成功物化的配置照常生效 |

返回 =(:groups :projects :errors :bootstrap-needed)=；=:errors= 顺序为「文件加载 → 项目引用校验 → 物化」。目录不存在时不创建目录，=:bootstrap-needed= 为 t。

* scope 语义

| 维度 | =shared= | =per-project= |
|------+----------+---------------|
| compose 项目名 | =ebc-shared=（固定） | =ebc-<project>= |
| 生成物位置 | =<cache>/_shared/compose.yaml= | =<cache>/<project>/compose.yaml= |
| 容器集合 | 全局一套，跨项目共用 | 每个项目一套 |
| 配置份数 | 至多 1 份，=:project= 必填 | 每项目 1 份（可多项目各 1 份） |
| =down= | *不提供*（别的项目可能正在用） | 提供（=down=，不带 =-v=） |
| 状态匹配 | 按 =:scope "shared"= + =:group= 匹配，*忽略* =:project= | =:project= + =:group= 都相等才命中 |

要点：

- shared 组的配置里 =:project= 是 *宿主*（发起项目）：它只用于渲染上下文、生成物命名与 =ebasecamp.project= 标签归属，*不是业务绑定*；同一套 shared 容器可被任意项目通过 external network =ebasecamp= 访问。
- shared 容器的 =ebasecamp.project= 标签记的是发起项目，因此状态匹配必须按 =scope= + =group=（D8），按 project 过滤会漏掉其他项目发起的 shared 容器。
- 全量渲染（=GROUP-FILTER= 为 nil，预览/导出）时，若被渲染的引用全为 shared，compose 项目名仍是 =ebc-shared=，否则 =ebc-<project>=；按 scope 渲染（=GROUP-FILTER= 非 nil）时各自命名。
- 项目名的字符集约束 =[a-z0-9_-]+= 由 =ebasecamp-compose--name-string= 校验，组名同样受约束。

| 15 | 项目 =:root= *可选*：为 nil 时不参与目录定位、不作路径基准（派发不带 =--project-directory=、相对 =file:= 预校验只给 warning）、导出须显式选路径（无 =:root= 无 =:export-file= 时交互式 =read-file-name=、非交互报错）；写盘 =update-project= 清空须用 =clear-root=（键真删，不留 =:root nil=） | 把 nil 当「不改」以外的东西 → 只改 =:title= 就删掉 root；写成 =:root nil= → =plist-member= 判定把「键存在」与「无根目录」混淆；让 nil 参与定位 → 所有无 root 项目争同一个「最长前缀」 |

第 5 条的三个 flag 缺一不可，缺 =--no-interpolate= 时退出码仍为 0（静默失败），因此只能靠代码审查 + 密钥断言测试守住。

* 刷新链路

一次状态刷新是「单一 =state= ref + 整树 patch」：

1. =ebasecamp-status-start= 在 UI 挂载时启动：立即刷一次，之后每 =ebasecamp-status-refresh-interval= 秒（默认 3）执行 =ebasecamp-status--tick=。
2. =ebasecamp-status-snapshot= 调 =ebasecamp-docker-ps= （=docker ps -a --no-trunc --filter label=ebasecamp.managed=true --format '{{json .}}'=），归一为状态记录写入 =ebasecamp-status-last-records=；失败不 signal，错误留在 =ebasecamp-status-last-error=，旧记录保留。
3. 轮询回调调用 =ebasecamp-ui-refresh= 并传入 =last-records= + =supplied-p= t：明确告诉刷新「已经采集过」，因此一次刷新只跑一次 =docker ps= （空表也算已采集）。
4. =ebasecamp-ui--build-state= 构建整棵树的渲染数据：每组经 =ebasecamp-data-group-instances= 装配一次实例（每份配置一项），=:running= / =:total= 由记录逐级汇总。
5. =etaf-set-value= 把 state 写回会话的 =state= ref；渲染期读过该 ref（=etaf-value=）的节点全部重建 —— 顶栏统计、左栏组树与展开状态、右栏各段的服务表一起更新。

为什么不用 =etaf-data-grid=：它没有分组能力（实测），而 v0.2 的右栏是「选中组 → 每份配置一个 =etaf-panel= 段 → 段内一张服务表」的两级结构，且每段需要自己的段头（配置名 → 项目、scope 徽标、running/total、三个按钮）。因此段内一律用 =etaf-table= （不绑数据源，行直接来自 plist 记录），配合单一 =state= ref 做整树 patch 即可，无需额外同步机制。

轮询的启停与 UI 生命周期绑定：=etaf-on-mounted= → =ebasecamp-status-start=；=etaf-on-unmounted= / =ebasecamp-ui-close= → =ebasecamp-status-stop= + 取消提示定时器。

* UI buffer 身份与键位分层

=*ebasecamp*= 不是可以随便打字的 buffer，而是清单的投影。这一节记录实现里必须守住的几条机制，顺序从 buffer 身份到键位分层。

** buffer 身份：从 =special-mode= 派生并且只读

主模式 =ebasecamp-ui-mode= 用 =define-derived-mode= 从 =special-mode= 派生，body 里设 =buffer-read-only= 为 t。启用时点在同一次 =ebasecamp-ui-open= 里早于 =etaf-mount= ，顺序不能反。

原因是 =special-mode= 会执行 =kill-all-local-variables= 而清掉 ebox 的 buffer-local 挂载状态，即 =ebox--buffer-mount= 变量。若「先 mount 再设 mode」，随后 =ebox-node-at= 与 =ebox-focus-scope= 会报 =No mounted Ebox tree= 错误，焦点与键层全部失效；而渲染断言比对的是 buffer 文本，仍然全绿，属隐蔽失败。U1 实测即为此：计划原写「mount 之后设 mode」，实测必须改成之前。

只读不阻断渲染：etaf 写 buffer 时自己用 =inhibit-read-only= 关掉只读，因此 mount 后整树 patch 照常更新，而 =buffer-read-only= 全程保持 t，首帧渲染未被阻断。

** 键位三层与优先级

从高到低：

| 层 | 内容 | 效果 |
|----+------+------|
| etaf Host =:keys= | 根 Host 21 条由 =ebasecamp-ui--root-keys= 提供，段 Host 5 条由 =ebasecamp-ui--section-keys= 提供；此外有框架默认的 =?= 帮助 / =TAB= 与 =S-TAB= 焦点移动 / =RET= 激活 / 方向键 | 装在 =emulation-mode-map-alists= 最前面，因此能遮住 evil |
| evil emulation map | =i= 进 insert state 等 | 未装 evil 时不存在；装了也被上一层的 local 边界吞掉 |
| =ebox-buffer-mode= 的 =suppress-keymap= | 未绑定键的兜底抑制 | 优先级最低，挡不住 evil |

结论：界面内 evil 的 =i= 之所以不进 insert，靠的是 *etaf 键层把它吞掉* 这个机制，而不是 =special-mode= 或 =suppress-keymap= 。

** 键位来源：事实源 → 渲染索引 → 按钮文案

键位信息在实现里分三层，方向是单向的（渲染层只能读事实源，不能反过来定义键位）：

| 层 | 载体 | 角色 |
|---+---+---|
| 事实源 | =ebasecamp-ui--root-keys= （21 条）/ =ebasecamp-ui--section-keys= （5 条） | *唯一* 键位定义：键名 + COMMAND + 中文 LABEL；=etaf--keys= 从这里取，=?= 帮助也从这里取 |
| 渲染索引 | =ebasecamp-ui--button-key-hints= （=((按钮文案 . 键名) …)= ，6 条） | 只回答「这个按钮该显示哪个键」，*不* 定义键位、不参与按键分派 |
| 渲染结果 | 按钮的 =[KEY] LABEL= 前缀（=ebasecamp-ui--button-label= 拼接） | 纯显示层产物，=KEY= 为 nil 时逐字节等于原 label |

- *拼接发生在渲染层*：=--footer-button= / =--section-button= 各接受一个可选 =KEY= ，而 *调用方传的 =label= 参数值不变* 。这是硬约束：=--goto-section= 用 =(search-forward "启动选中")= 定位段头（锚点就是文案），测试 =header-buttons-disabled-when-busy= 断言的是 label 参数而非渲染文本 —— 参数层零变更，两处锚点都不破。
- *一致性判据*：测试 =button-key-hints-match-key-tables= 断言 ① 索引里的每个 KEY 必须存在于某张键表；② 命中条目的键表 LABEL 必须 *按序包含* 按钮文案（subsequence）。第 2 条 *不是前缀判据* —— =(string-prefix-p "启动选中" "启动该段选中")= 实测为 nil（第三个字符是「该」），前缀判据在段级不成立；按序包含是弱一些但可机械检查的约束，局限记在 ADR-0010 的「已知边界」与技术债 #45。
- *为什么不合并成一张表*：把按钮文案直接当键表 LABEL 会破坏「帮助文案可独立演进」与「按钮文案短于帮助文案」这两个既有约定。索引表只承载两者之间的 *翻译* ，漂移由测试兜住。

** 勾选列定位改用 ref 自校验

测试助手 =ebasecamp-ui-test--goto-first-checkbox= 原先用裸 =(search-forward "[")= 找勾选列。v0.6 给段头按钮加了键提示（=[s]= / =[x]= ）后，它先命中 *段头按钮的提示* （段头在服务表上方），=--checkbox-ref-at-point= 解出 nil，既有用例随之变红。

「只认 mark 字形」也不行：=etaf-ui= 的 checkbox 只产出 =[ ]= 与 =[x]= ，而 =[x]= 同时是「停止选中」的键提示，文本层不可区分。现在的做法是 *候选 mark + ref 自校验* —— 逐个尝试 =[ ]= / =[x]= ，只有能解出 checkbox ref 的才算命中，按钮提示里的 =[x]= 因解不出 ref 被跳过。定位因此与按钮文案、键提示格式完全解耦。

** 吞键条件

etaf 只在 *边界 Host* 内吞掉未绑定的 printing key。边界指 =:key-scope= 为 =local= 或 =:focus-scope= 为 =modal= 的 Host，当事件是 printing key 且键链末端落在该边界时返回 =#'ignore= 值。两个必要细节：

- 边界必须在 *最外层* Host，也就是 =ebasecamp-ui-app= 的 render 里那个全 stretch 的 =box= ：它统一包住 empty 与非 empty 两个分支，并把 =:key-scope 'local= 与 =:keys= 都写在上面，因此覆盖全 buffer；子树上的边界只在其子树内生效，段级键就装在每份配置的段 Host 上。
- 无焦点时键链以 =ebox-focus-scope= 兜底，取的是 mount root，所以冷启动也安全 —— 打开界面后没按过 =TAB= 与方向键就按 =i= ，同样被吞掉。

框架保留键由 etaf 拥有，包括 =escape= / =M-g= / =C-g= / =?= / Tab 系列 / 四个方向键，应用侧绑定会被 =etaf--keys-validate= 拒绝。另有 =C-x= / =M-x= / =C-g= / =ESC= 不受 local 边界影响，仍按 Emacs 原生语义走。

** mode-map 绑定只作装饰

=ebasecamp-ui-mode-map= 里重绑了 =q= 与 =g= 两个键。其中 =q= 覆盖 =special-mode= 默认的 =quit-window= 并指向 =ebasecamp-ui-close= ，而 =g= 指向 =ebasecamp-ui--reload-and-refresh= 。但 major-mode map 上的 printing key 会被 etaf 的 runtime 键层遮住 —— =lookup-key= 能命中，而 =key-binding= 却返回 =ignore= 值（U1 实测）。因此这两条只是「etaf 键层不可用」时的兜底，界面内按键必须声明在 Host 的 =:keys= 里；新增键不要指望 mode-map 生效。

** =SPC= 不可重绑，行级勾选改用 =t=

=SPC= 的事件向量是 =[32]= ，属于 ebox 的 =ebox--activation-keys= 列表（与 =RET= / =mouse-1= 同组），以 *节点级 char-property keymap* 安装，按键查找顺序先于 =emulation-mode-map-alists= 。三个后果：

- 根 Host =:keys= 里的 ="SPC"= 条目 *永远不执行* 。同一张表里的普通字母立刻生效，说明键层本身正常，只是收不到这个事件。
- =etaf-activate= 作用于 *焦点宿主* ，包括按钮。所以 =SPC= 不能当勾选键：point 在「启动选中」上按 =SPC= 会直接把容器起起来。
- =etaf-button= 不接受 =:keymap= 覆盖，会报 =Unknown prop or Host attribute :keymap= 错误，没有 per-node 绕过的途径。

因此 =SPC= 保持 ebox 的「激活当前控件」语义，勾选框上勾选、按钮上按下，与 =RET= 等价；行级切换另绑 =t= ，它是 printing key，由本应用的键层处理，在按钮上不会误触。

** =t= 的实现前提：行必须可交互

服务表的 =:row-ref= 只有在同时传 =:on-row-press= 时才被采用，判定逻辑在 =etaf-ui--table-row-node= 的 =interactive-p= 分支里；否则行 Host 退回实例内生成 ref，于是 =t= 就取不到行身份。副作用有两个：行变为可聚焦，TAB 停靠点因此增加；点击行、或焦点在行上按 =RET= 时也会切换该行勾选。三者写的是同一个 =ebasecamp-ui--toggle-selected= ，不存在第二套选中表示。

** 段级键位与段内按钮同源

=ebasecamp-ui--section-keys= 的闭包 *捕获该段自己的 instance* 再调 =ebasecamp-ui--section-action= ，与段头三个按钮完全同一条派发路径。段级全选与全不选分别用 =a= 、 =A= ，两者调的都是 =ebasecamp-ui--select-instance= 。刻意不引入「当前段」全局状态，因此同组多实例不会串段。

** 焦点优先于 point

根 Host 的 =:key-scope 'local= 使 =etaf--keys-chain= 在任何焦点存在时 *从焦点起算* ，而不是从 point 起算。于是 Tab 定位过控件之后，段级键跟随焦点所在段，可能与光标所在段不同。这是「与段内按钮一致」的代价：按钮同样按焦点宿主激活。

** 编辑入口边界

UI buffer 只读，写操作有两条路，但 *共用同一写盘事务内核* （见「清单写盘」一节）：

1. *界面表单*（v0.5 起）：=S= 编辑 point 所在服务的 6 个字段、=E= 改配置的 =:project= 、=M= 移动配置、=X= 打开清单操作菜单（配置 / 项目 / 组的 CRUD）。这些入口只在界面 buffer 里收键，实际写入由 =ebasecamp-config-write.el= 调 =ebasecamp-manifest--write-transaction= 完成，界面 buffer 本身仍然只读。
2. *手写清单*：=ebasecamp-ui-edit-manifest= （根级键 =e= ）取会话的 =selected-group= ，先用 =ebasecamp-config-write--manifest-file-for-group= 按组名 *跨文件定位组定义实际所在的文件* （=groups.el= 与 =projects/*.el= 皆可——组定义在哪个文件，就打开哪个文件），再在该文件里定位到 =(ebasecamp-define-group <组名>= 那一行。三档降级都不阻断编辑：无选中组走 =user-error= ；定位失败（清单里没有该组 / 同名组重复定义）先 =message= 说明原因，再退回 =groups.el= （不存在则退到第一个项目文件），连可编辑的清单文件都没有才 =user-error= ；文件里搜不到 =(ebasecamp-define-group <组名>= 时退到 =point-min= 并 =message= 提示，*不 signal* （清单可以手写，定位失败不该阻断编辑）。函数只打开文件，不读取也不打印任何密钥值；保存后的重载由 =g= 走 =ebasecamp-reload= 完成。

无论走哪条路，「写」最终都落在清单文件上：表单路径经事务内核（含备份、原子写、错误集差分回滚），手写路径由用户自己保存。ADR-0003 的决策 6（唯一写入口 = =e= ）已由 ADR-0005 扩展，界面 buffer 只读这一条不变。

* 布局与主题

v0.4 把主界面从「一个内容自然增长的 =column=」改成「总高恒等于窗口高的 flex 三段式」，并让配色跟随 Emacs 主题、让三个区域各自可滚、可跳转。这一节记录实现里必须守住的机制与实测边界；逐批次实测数据见 =openspec/completed/2026-10-23-ui-layout-theme-nav.md=。

** flex 三段式（没有 sticky bottom 可用）

底栏要固定，先得否掉「靠定位属性钉住」这条路：etaf 的 =:sticky= *只支持 top*（实现是写 header-line，每 Runtime 一个、限单行），=:position= 只有 =static= / =relative= / =absolute= 三种，没有 fixed。因此唯一可行解是让 *根节点总高等于视口高*、整窗不产生滚动，底栏自然落在最后一行。

渲染结构（=ebasecamp-ui-app=）：

| 层 | 节点 | 关键属性 |
|----+------+----------|
| 根 | =flex= | =:flex-direction 'column= + =:width 'stretch= + =:height 'stretch= |
| 顶栏 | =row= | =:width 'stretch= + =:flex-shrink 0= |
| 中间区 | =box= | =:width 'stretch= + =:flex-grow 1= + =:min-height '(lh 0)= |
| 底栏 | =flex= | =:flex-direction 'column= + =:flex-shrink 0=（=:ref 'ebasecamp-ui-footer=） |

四条硬约束：

1. *根必须是 =flex=，不能是 =column=*。只有 tag 为 =flex= 的节点进 =ebox--layout-flex=；=column= / =row= *不走 flex 分配算法*，写在它们子节点上的 =:flex-grow= / =:flex-shrink= / =:min-height= *全被忽略*。实测对照：根写 =column= 时根内容高 32 > 视口 20、底栏下沿掉出视口、buffer 里连「底栏」文本都没有，且 =etaf-scroll-by= 恒返回 0（中间区拿不到限高 → 滚动恒定无效）。
2. *顶栏与底栏都要显式 =:flex-shrink 0=*。漏写时会被压缩到 0 行，文本直接从 buffer 消失（不是「看起来挤」）。
3. *中间区 =:flex-grow 1 :min-height '(lh 0)= 承担全部收缩*。这是「整窗不滚」的关键：漏写 =:min-height '(lh 0)= 时中间区拒绝收缩，整窗继续滚动。
4. *flex 只接受 =:row-gap= / =:column-gap=*，纵向间距不能写 =:item-gap=（实测 =Ebox flex rejected properties=）；=:column-gap= 只接受 =(px ch vw %)=，不吃 =(lh N)=。详见 [[file:../openspec/tech-debt.md][技术债]] #28。

** 区域内部滚动的前提

左右两个 pane 各包一层 =column :height 'stretch :overflow 'scroll=，高度 *由父 flex 约束*，不写死 =(lh N)=。两个坑：

- *slot 里的 pane 必须显式 =:height 'stretch=*：=etaf-splitter= 的 =&key= 白名单里没有 =:flex-grow= / =:min-height=，它自己不能撑高；pane 不写 =:height 'stretch= 时高度退化为内容高（=vh == ch=），=etaf-scroll-by= 恒返回 0，滚动区静默失效。
- *内容列自带 =:height 'stretch= 时要垫一层 =box=*：滚动容器的 =ch= 计的是子节点 border-box，子节点被拉成「滚动视口高」后 =vh == ch=，仍然滚不动。右栏内容列正是自带 =:height 'stretch= 的情形，因此中间垫了一层高度取内容的 =box=，内容恢复自然高度后才会溢出、才会滚。

滚轮按「最内层滚动器优先」分派（=ebox--scroll-chain=），所以左树与右栏互不干扰，顶栏与底栏在滚动时几何完全不变（实测滚动到 end 后底栏 =ebox-node-geometry= 与滚动前一致）。

** 主题两层与主题钩子

配色分两层，色值字面量 *只允许* 出现在 =ebasecamp-ui--palette-light= / =-palette-dark= 与 =defcustom= 默认值里，render 区一律走 =etaf-theme-token=（由测试的 render 区字面量扫描机械守护）。

1. *基础色（9 个）从 face 取*：=:ui-fg= / =:ui-bg= 取 =default= 的前景 / 背景；=:ui-panel-fg= / =:ui-panel-bg= 取 =mode-line-inactive= 的前景 / 背景；=:ui-muted-fg= 取 =shadow= 前景；=:ui-border= / =:ui-panel-border= / =:ui-divider-bg= / =:ui-table-border= 走 =fringe= 前景 → =mode-line-inactive= 背景 → palette 的两级回退。
2. *状态色（26 个）走内置 palette*：success / warning / danger / info / accent / disabled / button / checkbox / table-selected 的 fg / bg / border，按 =(frame-parameter nil 'background-mode)= 选 light 或 dark。合计 *35 个 token*。

=face-attribute= 有三种「无值」形态，逐一都要兜：①*伪色字符串* —— 无主题时 =default= 的前景 / 背景是 ="unspecified-fg"= / ="unspecified-bg"=（字符串，=symbolp= 为 nil）；②*符号 =unspecified=* —— =shadow= / =fringe= / =mode-line-inactive= 在无主题时全是它；③*未定义 face 直接抛错* —— =(error "Invalid face")=，用 =condition-case= 兜住。回退方向是「palette 同名键」，*不是* 回退到 =default= 的同属性（否则自指）。

=etaf-theme-provide= *只能在 =:setup= 阶段调用*：render 期调用会被 =etaf--assert-not-rendering= 拒绝并 signal =etaf-render-side-effect-error (provide-context)=。传 =etaf-ref= *本身*即可（不要 =(etaf-value …)=），取值变化后同一节点身份的 =:bgcolor= 就地刷新，不重挂载整棵树。

主题切换靠 =enable-theme-functions= / =disable-theme-functions= 两个 abnormal hook（Emacs 29+）：=ebasecamp-ui-open= 在 =etaf-mount= *之前* =add-hook= 并重算一次，=ebasecamp-ui-close= 的 *第一行* =remove-hook= —— 挂载与卸载严格对称，任何后续失败都不会残留钩子。回调无脑重算整份 plist（face 与 =background-mode= 都是全量状态，按主题增量推断必然漏）。

** ui-state.el 是运行时状态缓存

左栏宽度持久化到 =<ebasecamp-cache-directory>/ui-state.el=，内容只有 =(:split-ratio FLOAT)=。

- *不是清单*：不参与 =ebasecamp-config-load=、不经界面 =e=（编辑清单）入口、可随时删除（下次打开回默认）。因此它 *不破坏* ADR-0003 的「清单唯一写入口 = =e=」不变量。
- *写入*：目录不存在时 =make-directory= 递归创建；先写同目录 =make-temp-file= 的唯一临时文件，再 =rename-file= 原子覆盖 —— 避免写一半留下损坏文件。写盘失败只 =message= 不 signal（本函数在 =close= 与拖动回调里调用）。
- *读取*：只接受 =(:split-ratio NUMBER)= 单一形态，其余（空文件 / =(foo)= / 裸字符串 / ratio 为字符串）一律按非法回退 defcustom 默认；读到数字后 *钳制到 [0.15, 0.55]* —— 越界值不钳制会在渲染期被 =etaf-check-prop= 判死、界面打不开。
- *不执行文件内容*：Emacs 31.1 起 =#.= 读语法默认禁用，且 =read-eval= 变量 *已不存在*（=boundp= 为 nil，照旧写 =(let ((read-eval nil)) …)= 会因「变量未使用」被 =byte-compile-error-on-warn= 判死）。替代做法是读前显式拒绝含 =#.= 的文本：合法状态文件永不含该序列，语义在 31.1 与旧版（=read-eval= 默认 t）上都成立。

** 区域跳转

etaf *没有* 「跳到某个 group」的 API，可用的是 =etaf-focus-within=。三条实测结论决定实现形态：

1. *nil COUNT 就是「子树第一个停靠点」*，不需要传 count（零值只查询焦点是否在内）。
2. *缺失 Host 会 =user-error=*（经 =etaf--event-host-node= 报 =No committed ETAF Host=），所以调用前必须判 =(etaf-runtime-host-node runtime ref)= 非 nil；runtime 也必须取自 *当前 buffer*（=(etaf-runtime-for-buffer (current-buffer))=），在别的 buffer 里误触自然 no-op。三类静默 no-op：未知区域、无已挂载运行时、该区域未渲染（空清单没有底栏）。
3. *真实停靠点不是区域 Host 本身*，而是区域子树里第一个可聚焦控件，因此契约只能是「焦点进入该区域子树」。

=1= / =2= / =3= 绑的是 *三个零参命令*（=--focus-tree= / =-detail= / =-footer=）而不是带 =interactive= 的 =--focus-region=：=etaf--keys-run= 对 commandp 条目走 =call-interactively=，直接绑带 interactive 参数的函数会在按键时先弹 =completing-read= 问区域。

** 项目定位

=ebasecamp-ui--project-for-directory= 按「最长 =:root= 前缀」找当前目录所属项目，三条要点：

- *双归一*：DIR 与每个项目 =:root= 都先 =expand-file-name= 再 =file-truename=，然后统一成 =file-name-as-directory= 形态 —— =~=、=..=、软链因此等价，且只匹配 *整段目录*（=/tmp/a2= 不会被 root =/tmp/a= 命中）。
- *大小写敏感*：=string-prefix-p= 不传第三参数也不绑 =case-fold-search=（=/tmp/A= 与 =/tmp/a= 是两个目录）。多个命中时取 root *最长* 者（=/a/b/c= 同时命中 =/a/b= 与 =/a= 时取 =/a/b=）；=:root= 为 *nil*（无根目录项目，v0.5.3 起写盘与界面均支持）、为空串、或目录不存在时 *跳过*。
- *「第一份配置」的顺序契约*：按 =ebasecamp-model-groups= 的组顺序、组内 =:configs= 顺序，取首个 =:project= 命中的配置所在组 —— 只由清单的组定义顺序决定，不看项目 =groups= 槽（物化产物里也有该组，但物化顺序不是契约）。
- *无匹配不选中*：命中不到项目、或该项目没有配置时，保持既有「无选中组」态（右栏显示「选择左侧的组」），*不是* 回退到第一个组 —— 自动选中会删掉未选中态。
- *只算一次*：定位只在 =ebasecamp-ui-open= 建会话时算，=ebasecamp-ui-refresh= / =g= 都不覆盖用户手选的组；关闭后重开才重算。

* 清单写盘

v0.5 把「界面只读 + 手写 Elisp」扩展成「界面可改，但写盘走同一个事务内核」。实现集中在两个新模块：=lisp/ebasecamp-manifest.el= （纯文本层：定位 / 替换 / 追加 / 删除 form、生成器、写盘事务）与 =lisp/ebasecamp-config-write.el= （字段映射 + 实体操作 + 引用扫描）。=ebasecamp-import.el= 的三个生成器改为调用 manifest 的薄壳，避免两处格式漂移。设计决策见 [[file:adr/0005-manifest-write.org][ADR-0005]]。

** form 定位（=ebasecamp-manifest--scan-forms=）

不自己写扫描器：=with-syntax-table emacs-lisp-mode-syntax-table= 下逐段 =forward-comment= 跳过空白 / 注释，再 =read= 一个顶层 form，用读前读后的 =(point)= 记下区间与 =(kind . name)= （=kind= 取 =group= / =project= ，其余 form 两者皆 nil）。

三条实测出来的边界：

1. *位置是 1-based*。=read= 前后的 =(point)= 是 buffer 位置，做字符串切片必须 =(1- pos)= 。扫描器返回的 =:start= / =:end= 一律按位置使用，调用方自己减 1，不预先转成下标 —— 否则每层调用都要猜「这是位置还是下标」。
2. *=read= 自己会跳过 =;= 行注释*。早期 docstring 里「read 不认 =;= 注释」的论断在 Emacs 31.1 上不成立（已修正）。=forward-comment= 保留只为与既有实现口径一致，它不是「否则必失败」的前置条件。
3. *=#| |#= 块注释不支持*。=forward-comment= 与 =read= 都不认（后者直接 =invalid-read-syntax= ），扫描器用 =search-forward "|#"= 跳过并记一条 note、=#|= 未闭合时 =user-error= ，但这只是防御性能力：*实测 =load= 本身也不认块注释*，带块注释的清单 =ebasecamp-config-load= 会直接报错。因此写入路径 *绝不生成* 块注释 —— 这是「扫描器能跳过」与「写入可以产生」之间必须切开的一条线。

替换只替换目标 form 的区间，form 之外的字节（文件头、块间注释、兄弟组、尾随 form）逐字节保留；多处替换用 =--replace-forms= 按 =:start= *降序* 应用，前面替换的长度变化不会影响后面位置。写盘路径必须在 *同一份内存全文* 上定位（=--scan-text-forms= ），不能重新读盘 —— 否则 mtime 快照与原子性同时失效。

** 跨文件定位（=ebasecamp-config-write--manifest-file-for-group=）

清单里的组可以定义在 =groups.el= ，也可以定义在任意 =projects/*.el= （导入功能默认把「组 + 项目」一起写进 =projects/<name>.el= ），因此写操作 *不能假定目标文件是 =groups.el=* 。定位分两层：

1. *收集*：=--group-manifest-files= 遍历 =ebasecamp-config--files= （顺序恒为 =groups.el= （存在时）→ =projects/*.el= 字典序，后者由 =--project-files= 用 =string<= 排序），只保留 *含组 form* 的文件（不含组 form 的文件不可能定义组，跳过不改变结果）；=--group-files= 在同一批文件里收集定义指定组的 *全部* 文件，不做唯一性裁决（供 =add-group= 查重与引用扫描复用）。
2. *裁决*：0 命中 → =user-error= 「清单里没有组 X（已扫描 N 个文件）」；>1 命中 → =user-error= 「组 X 在多个文件中定义（<文件列表>）；请先清理重复定义——同名组会让后加载的文件整体回滚，其中项目不会出现在界面中」；1 命中 → 返回该文件绝对路径。

不能复用 =ebasecamp-manifest--locate-form= ：它明确「同名多个时返回第一个」，语义只适合「在同一份已扫文本里取唯一 form」（=--replace-form= / =--remove-form= 的前提）。跨文件的 *文件裁决* 是另一个问题 —— 同名组在加载层就是硬错误：=--register-group= signal「组 X 已定义」，并且 *后加载的文件整体回滚* ，同文件里的项目定义一起消失、不会出现在界面中（X0.1 实测）。静默取第一个会让「改完没效果」而无从判断，因此必须拒绝并说明后果。

八个写入口（=update-service-fields= / =-add-config= / =-update-config-project= / =-remove-config= / =-move-config= 的源组与目标组各自定位 / =-update-group= / =-remove-group=）都先定位再开事务；=--edit-manifest= 签名改为 =(FILE EDITOR)= ，=ebasecamp-ui-edit-manifest= 定位失败时降级为打开文件头 + =message= （不阻断）。=add-group= 是例外：新组固定写 =groups.el= （不存在则新建），但写前用 =--group-files= 扫 *全清单* 查重 —— 否则新建的组会与项目文件里的旧组构成同名组，下次加载整体回滚。

引用扫描的口径随之分化，且 *故意不同*：=--config-references= （删项目前的引用保护）改为遍历 *所有含组 form 的清单文件*，允许多命中 —— 引用扫描只需全覆盖；=--legacy-group-references= （删组前）继续只遍历 =projects/*.el= ，因为它扫的是项目 form 的 v0.1 旧写法 =:groups= 。

** 写盘事务（=ebasecamp-manifest--write-transaction=）

七步，顺序不能变：

1. 读原文 + 快照 =(file-attributes)= 的 *mtime + size* ；同时快照当前 =ebasecamp-config-load= 的 *错误集* （=ebasecamp-config-error-messages= 取 =:errors= 的 =:message= 列表）。
2. 调 WRITE-FN 在 *内存里一次* 得到新全文。WRITE-FN 内不许分两次写盘 —— 移动配置的「源组移除 + 目标组追加」必须在同一次全文改写里完成，否则会出现「源删了、目标没加」的中间态。
3. *写前再 stat* ：mtime 或 size 任一变化 → =user-error= 「文件已被外部修改，先 =g= 重载」。mtime 精度在某些文件系统上是 1 秒，size 兜底。
4. 备份原文（同目录 =.ebasecamp-backup-*= 隐藏文件，*不带* =.el= 后缀以免被加载器读到）。
5. *原子写*：同目录 =make-temp-file= + =rename-file= 覆盖，沿用原文件权限位。符号链接在事务开始时即拒绝（=rename-file= 会替换链接本身而不是目标）。
6. 重新 =ebasecamp-config-load= 取新错误集，=cl-set-difference= 出差集；*仅当出现「写前没有的新错误」时才回滚* 。判据是 *错误集差分* ，不是「错误为空」也不是「条数」—— 语法错一次会产生 2 条错误，且用户其它文件里可能本来就有错，用「零错误」当判据会让既有错误永久阻断写盘。
7. 成功删备份并返回加载结果；回滚 = 用备份恢复原文 + 删备份 + 重新加载 + =signal 'ebasecamp-config-write-error= （data 含新错误摘要、原文件路径、备份路径）。恢复本身失败时 *保留备份* 并在 message 里给出手工恢复路径，不静默。

差分只比较 *消息文本* ，避免同一旧错误的行号 / 路径漂移被误判为「新错误」。mtime+size 检测与写入之间仍有 TOCTOU 窗口，单用户编辑器场景接受该窗口。

实体操作在写盘 *之前* 就做校验（D2 冲突 = 「同一项目同一组只允许 1 份配置」、组 / 配置 / 项目不存在、名字非法、scope 非法），选在原文 plist 上校验而非 model 对象：写前就能判定，避免把冲突变成一次无谓的写盘 + 恢复。

** 引用完整性（两处扫描不可混用）

- *删项目*：用 =--config-references= 读 =groups.el= 原文，按每个组 form 的 =:configs= 逐项比 =:project= ，返回「组/配置」字符串（如 =alpha/dev= ）。被引用即 =user-error= 并列出清单。
- *删组*：用 =--legacy-group-references= 遍历 =ebasecamp-config--project-files= ，=read= 每个项目 form 的 v0.1 旧写法 =:groups= ，按引用项 =car= 比组名。被引用即 =user-error= 并列出项目名。

两处都 *读原文而不看 model* —— model 可能因既有加载错误缺定义，而引用判断必须看磁盘真实内容。删项目走 =--delete-file-transaction= （校验路径归属 → 记录原文与权限位 → =delete-file= → 重新加载 → 仅新增错误时写回原文并恢复权限位）；删组不需要它，组是 =groups.el= 里的 form，走 =--remove-form= + 写盘事务即可。

** compose 顶层 =configs= / =secrets=（模型与渲染）

compose 允许服务引用顶层声明的 config / secret。v0.5.1 之前这条链路有两处缺口：导入把顶层段 *静默丢弃* （服务级 =configs:= 经 =:extra= 透传，于是生成物里出现「引用存在、定义缺失」），渲染层也只输出 =name= / =services= / =networks= / =volumes= 四段 —— 结果是 =docker compose up= 报 =service "x" refers to undefined config= 。

现状：

- *模型*：=ebasecamp-project= 新增 =file-configs= / =file-secrets= 两个槽（放在 =export-file= 之后，保持既有槽位顺序），=ebasecamp-model--project-keywords= 加入 =:file-configs= / =:file-secrets= 。值必须是 nil 或「元素全为 =(字符串键 . 值)= 的 proper list」；校验分 *入口* 与 *递归* 两层 —— 入口判形态，递归层下钻时允许标量，但 *凡是映射层（列表首元素是 cons）的所有键都必须是字符串* 。判据与渲染层 =ebasecamp-compose--mapping-p= 完全一致，于是「模型放行」与「渲染正确」是同一规则，不会出现「加载通过但渲染成垃圾 YAML」（=--yaml-map= 会把符号键当序列渲染，实测）。
- *导入*：=ebasecamp-import-parse-json= 把顶层 =configs= / =secrets= 存进项目结构；提示经动态变量 =ebasecamp-import--last-warnings= （每次导入重置）+ 访问器 =ebasecamp-import-warnings= 承载（如「顶层键 x-unknown 暂不支持，已忽略」），且 *不改变 =parse= / =parse-json= 的返回值* —— 仍是 project 对象，=ebasecamp-import-service-plists= 等既有调用点零改动。
- *落盘*：=ebasecamp-manifest-project-form= 只在非空时追加 =:file-configs= / =:file-secrets= （值经 =--literal= 原样 =prin1= ，=${VAR}= 与相对路径不插值）；无顶层段时输出与历史实现 *逐字节一致* 。=ebasecamp-config-write--project-output-keys= 同步加入这两个键并改为「非空才写」，因此 =-update-project= 改 title / root 时两个槽保值。
- *渲染*：=ebasecamp-compose--file-declarations-section= 用 =--yaml-map= 输出顶层段（键一层缩进 2、嵌套层 4），段顺序 =name= → =services= → =networks= → =volumes= → =configs= → =secrets= （与 docker 惯例一致）。是否输出由 refs 是否 *全为 shared* 决定：全 shared 时省略，故 =ebc-shared= 生成物 *不含* 顶层段；其余情况输出，于是 =ebasecamp-export--deployment-project= 的副本（只留 per-project refs）自然带上顶层段，导出侧无需改动。

已知边界：=content:= 多行字符串 *已支持* （v0.5.4 起多行值走 YAML 块标量，chomping 按末尾换行数取 =|-= / =|= / =|+= ；双引号标量转义换行与回车），=file:= / =external= / =name= 形态行为不变 —— 判定保真须用 =config --format json= 对比 =content= 字符串，=config -q= 只校验语法不校验内容；=shared= 生成物不含顶层段（shared 组服务引用顶层 config / secret 需自行处理）。

** 字段映射（表单文本 ↔ 结构）

六个字段的双向纯函数在 =ebasecamp-config-write.el= ，无 IO；解析失败一律 =user-error= 带 *行号* （1-based，空行占号但不参与解析），消息格式 =「第 N 行：<说明>，得到 "<原文>"」= 。

| 字段 | 文本 → 结构 | 结构 → 文本 | 边界 |
|------+------------+------------+------|
| =ports= | 每行 =HOST:CONTAINER= ；*单段 =N= → =((N . N))=* （只有容器端口） | *恒写两段*（=((80 . 80))= → ="80:80"= ，不折叠） | 非整数 / 负号 / 缺段 / 多冒号 → 报错 |
| =environment= | 每行 =KEY=VALUE= ，按 *首个* = = 切分 | =KEY=VALUE= 逐行 | 缺 = = / 空键 / 重复键 → 报错（重复键附首次出现行号）；=${VAR}= 原样 |
| =volumes= | =SRC:DST[:ro]= ；*源以 =.= 或 =/= 开头即 =:type bind= ，否则 =:type volume=* ；单段 =DST= → =(:target DST :type volume)= | 有 =:source= 写三段，缺源只写 =DST= | 段数 > 3 / 空段 / 第三段非 =ro= → 报错（=tmpfs=、=:rw= 不改写、直接报错） |
| =command= | 含换行 → 每行一个参数（行内空格保留）；不含换行 → 按空白切分 | 每行一个参数 | *只支持 exec 形式*；原值是 shell 字符串且用户未改动时 *跳过重写* ，不强制转换 |
| =restart= | =string-trim= 后空 → nil | 原样 | 四个枚举外的自由值（="on-failure:5"= ）原值往返 |
| =image= | =string-trim= ，空即报错 | —（单行） | 必填 |

*volumes 必须是 plist* ：=(:source S :target T :type bind|volume [:read-only t])= 。字符串列表会被 =ebasecamp-config-load= 拒绝，所以表单文本 → 结构必须产出 plist，而不是「字符串列表」。

服务字段更新 *不经 model 对象重建*：用 =read= 取该组 form 的原始 =:services= plist，只把被编辑的键替换为新值、其余键值原样带回，再生成该 *服务子 form* 文本并替换组 form 内对应的 =(服务名 …)= 子 form。这样 =healthcheck= / =labels= / =networks= / =extra= / =entrypoint= / =working-dir= / =user= / =depends-on= 全部保真，=command= 原为字符串就仍是字符串。*某字段被清空 = 删除该键*（传 nil），不是写空串；*未改动的字段直接跳过重写* 。

** UI 表单边界

服务编辑框是 =etaf-dialog= ，四条实测约束（=lisp/ebasecamp-ui.el= 的 Commentary 与代码注释同源）：

1. *dialog 的 buffer 文本永远不含内容*（root-layer 投影）。因此测试只能断言 *ref 层* ：预填后读 6 个字段 ref 的值、非法保存后读 error ref 非空且 =:open= 仍为 t。*不能* 断言渲染出来的可见文本。
2. *字段 ref 必须在组件的 =:setup= / =:bindings= 创建* ，不能在 =:render= 里建；字段值全部经 =etaf-ref= 承载，回调读回。
3. *:ref= 只接受 symbol / function / nil* 。传 =etaf-ref= 对象会报错 —— 字段用 =:bind= 绑 ref，按钮用 symbol ref。
4. *=slot :name 'footer= 必须是 dialog 的直接子项*（嵌进 =column= 会报 =Unresolved View item: footer= ）。保存 / 取消按钮与错误 label 都放在这个 slot 里。

保存流程：先在本地跑一遍字段解析做校验，失败只更新 error ref、*不关闭* dialog；通过后走 =etaf-next-tick= 调写盘（让「保存中」状态先渲染），写后 =ebasecamp-reload= + 刷新并恢复选中组，成功 notice，最后关闭 dialog。dialog 不能同步返回用户输入，需要同步输入的地方（选项目 / 选组 / 输入名字）一律 =etaf-call-with-input= + =completing-read= / =read-string= ，与既有 =I= / =o= / =e= 一致。

** 派发参数构造与路径基准（=ebasecamp-command-compose-args=）

compose 命令行的唯一构造点是 =ebasecamp-command-compose-args (ACTION FILE PROJECT-NAME SERVICES &optional ROOT)= ：

#+begin_src text
compose -f FILE [--project-directory ROOT] -p NAME <subcmd> ...
#+end_src

- =ROOT= 非 nil 时在 =-f FILE= 之后、子命令 *之前* 插入根级 flag =--project-directory= 与 =(expand-file-name ROOT)= —— 该 flag 属于根级选项，放子命令之后就报 =unknown flag=；=-p= 仍显式传入，项目名不漂移；
- =ROOT= 为 nil 时参数序列与 v0.5.1 *逐字节一致*（既有用例零改动）：退回「相对路径按 compose 文件所在目录解析」的旧基准；
- *为什么需要注入*：生成物在 =<cache>/<project>/= ，而清单里的相对路径（顶层 =configs= / =secrets= 的 =file:=、以 =.= 开头的 =volumes= 源、=env_file=）属于 *项目根*；不注入时 docker 一律按生成物目录解析（探针 T3 实测 =configs.<n>.file= 被解析成缓存路径），缺失只在容器创建阶段以 =bind source path does not exist= 暴露；
- *ROOT 从哪来*：=--preflight= 与 =--dispatch= 都取 =ebasecamp-command-run= 里的 *同一个* 项目对象（=ebasecamp-command--project=），即 *触发本次操作的项目*；=ebc-shared= 生成物也用它的 root —— shared 配置的 =:project= 只是渲染上下文，不参与推导；
- *与预校验同基准*：=ebasecamp-docker-check-compose (FILE &optional ROOT)= 注入同一个 flag，否则重现「=config -q= 通过、=create= 炸」（不变量 14）；
- *=:root= 为 nil 时的三条回退*（v0.5.3，不变量 16）：①本函数 =ROOT= 为 nil 分支 ⇒ *派发参数不含* =--project-directory=，退回「按生成物目录解析」的旧基准；②=--missing-file-declarations= 对相对 =file:= *只记 =:preflight-warnings=*（不判缺失、不失败），UI 在成功提示末尾追加「（N 条预校验警告）」；③导出走 =ebasecamp-export--target-or-prompt= —— 无 =:root= 也无 =:export-file= 时交互式弹 =read-file-name=、非交互仍 signal，且 =--relative-path-notice= 在 root 为 nil（或目录不存在）时不提示。三条都只是「没有基准时的降级」，*不* 改变「=:root= 是相对路径唯一基准」的语义（设计见 ADR-0008）；
- *副作用*：注入后 docker 会读取 =<root>/.env=（compose 默认行为，探针补证 5），其中的变量参与生成物解析；插件既不读取也不写该文件；
- *不注入的两处*：=ebasecamp-import.el= 读的是 *用户项目自身* 的 compose 文件，其所在目录即项目根，基准本就正确（ADR-0007 记明该理由）；=ebasecamp-export.el= 的 =check-compose= 也 *不传 root* —— 导出目标由用户选定，校验基准 = *导出文件所在目录* = 部署基准（v0.5.3 技术债 #35 按此结论处置：不改基准，改为在「导出目录 ≠ 项目 root 且 root 真实存在」时 =message= 一次提示，见 =ebasecamp-export--relative-path-notice=）。

** 启动前预校验（=ebasecamp-command--preflight=）

生成物是否合法原先只在 docker 那一步暴露：=up= 直接失败，界面只看到 =invalid compose project= 这类笼统 stderr。v0.5.1 把校验前置到 =ebasecamp-command-run= —— 位置在 =check-requires= 之后、=ebasecamp-command-ensure-network= *之前* ，因此生成物不合法时连 external network 都不创建（零副作用），随后才建网络并派发。

实现要点：

- *逐分支写 + 逐分支校验，但不派发*：=--preflight (OBJECT BRANCHES)= 对本次要用的每个分支（shared 与 per-project 各算一个）调 =ebasecamp-compose-write= 写生成物、再调 =ebasecamp-docker-check-compose= 校验；只写盘与校验、不启动任何 docker 进程，所以「先全部校验、再统一启动」成立 —— 不会出现「已启动一部分容器、后面失败无法回滚」的部分启动。首个失败即停止后续校验（后面的分支连写盘都省掉）。
- *写盘不重复*：=--preflight= 把实际生成物路径以 =:written= 追加到分支 plist，*不复用 =:file=* —— =:file= 是 =--branch-shell= 预算的缓存路径，再追加会让 =plist-get= 取到前者并破坏既有用例断言；=--dispatch= 的 launch 改为「有 =:written= 就复用、没有（stop / down 等未预校验路径）就照旧写一次」。
- *失败载荷与成功路径同构*：失败时返回与 =--dispatch= 的 report 同字段的结果 plist（=:action= / =:project= / =:ok= / =:results= / =:auto-started-shared= / =:order= ），失败分支带 =:failed t= + =:exit= + =:stderr= 原文（UI 的 =ebasecamp-ui--report-result= 用 =ebasecamp-docker--first-line= 展示首行），其余分支标 =:skipped t=，=:order= 为 nil（一个都没派发）；=ebasecamp-command-run= 此时返回 nil。
- *动作范围只有 =start= / =restart=* （=ebasecamp-command--validated-actions=）：=stop= / =down= 不校验 —— 它们作用于已存在的容器，生成物暂时不合法时更应先允许把服务停掉。测试里把 =down= 的 =check-compose= 桩成 =error= 来守住这条不变量。
- *既有用例显式打桩 =ebasecamp-docker-check-compose=* ：此前它们只打桩 =run-sync= ，校验会经同一桩「侥幸」通过；显式打桩让用例不再依赖 =check-compose= 的内部实现。
- *两层检查，v0.5.2 加的是第二层*：=config -q= 只校验 =env_file= —— 顶层 =configs= / =secrets= 的 =file:= 缺失它照样 exit 0（探针 T2 / 补证 3），于是缺失要到 =create= 阶段才炸。因此在 *逐分支写盘与 =check-compose= 之前* 由 Elisp 侧自己核对：=--file-declarations= 只取 *本项目* 的 =:file-configs= / =:file-secrets= 中带 =file:= 的条目（=external: true= / 纯 =name:= 跳过），=--missing-file-declarations= 按 =ROOT= 判存在性 —— 绝对路径直接判，相对路径判 =<root>/<file>= ，无 =ROOT= 则 *只记 warning* 不判缺失。
- *缺失的失败载荷与 =check-compose= 失败同构*：=:failed t= + =:exit= nil + =:stderr= 可读消息「顶层 config `app_cfg' 的 file `./conf/app.conf' 不存在（基准：<绝对路径>）」，并落在 *per-project 分支* 上（=--project-branch-index= ，否则 UI 会把错误归到 shared 批次）。因此一个生成物都不写、一个 docker 进程都不派发（连 =network inspect= 都不执行）。
- *warning 不改变成败，但必须能到 UI*：warning 集合刻意命名 =:preflight-warnings= （不复用 =:warnings= —— 那是 =check-compose= 从 compose stderr 抽出的 =level=warning= 行）。透传链：=--preflight= 返回 → =ebasecamp-command-run= 的 *成功分支* 取 =:preflight-warnings= → =ebasecamp-command--dispatch (&optional PREFLIGHT-WARNINGS)= → report 的 on-complete plist 带 =:preflight-warnings= → =ebasecamp-ui--report-result= 成功分支在 detail 末尾追加「（N 条预校验警告）」。⚠ =--preflight-report= 是 *失败路径专用*，成功场景根本不经过它，不要在那里拼成功提示。

** 已知边界

- *服务子 form 内部的注释会丢*：替换子 form 时按生成器重渲染，排列也会被规范化（缩进对齐到原列，其余字节不动）。
- *组 form 整组重渲染会规范化排版*：改配置 / 移动配置走 =--replace-group= 重渲染整组，键序固定 title → scope → services → configs，服务子 form 与配置项各占一行；组 form *之外*（文件头、块间注释、兄弟组、尾随 form）逐字节保留。
- *移动配置会带走 =:services= 覆盖*：覆盖指向的组内服务名在目标组不存在时，写后产生新错误 → 事务 *整笔回滚* ，源配置原样保留（不静默丢数据）。
- *服务增删与改名不支持*：会让既有容器变孤儿，改名还要迁移容器标签与命名，需先有配置维度（技术债 #16 / #25）。
