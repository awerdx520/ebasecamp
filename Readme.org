#+author: Thomas
#+options: toc:t

ebasecamp 是 Emacs 里的 Docker 环境分组管理插件（版本 0.6.0）。

* ebasecamp 是什么

ebasecamp 把 Docker 环境按「组 → 配置 → 项目」组织：

- *组*（group）是可复用的基础组件集合（mysql、redis、应用栈……），是全局第一等对象，不依赖任何项目即可存在；组有 scope：=shared= 跨项目共用一套容器，=per-project= 每个项目一套。
- *配置*（config）挂在组内（组的 =:configs= 槽），用 =:project= 指向一个项目，并可为该项目覆盖端口、环境变量与卷。一份配置 = 一个「组 × 项目」实例，界面右栏给每份配置渲染一段。
- *项目*（project）是业务工程的容器，提供 =:title=、=:root=、=:shared-network=、=:export-file=。=:root= *可选*（留空即「无根目录项目」，见「compose 生成物与路径基准」）。

界面用 etaf / etaf-ui 在 Emacs buffer 内渲染：左栏「组 → 配置」树，右栏每份配置一段服务表，勾选服务即可批量启动 / 停止 / 重启。清单（组与项目定义）以 Elisp 形式保存在 =~/.config/ebasecamp/=，是唯一事实源；compose 文件只是由清单派生的生成物。插件还支持从已有 compose 文件导入清单，以及把项目导出为部署用 compose。

* 特性

- *组复用*：一个组定义可被多个项目引用（每份 =:configs= 一项）；=:scope shared= 的组跨项目共用一套容器（compose 项目名固定 =ebc-shared=），=:scope per-project= 的组每个项目一套（=ebc-<project>=）。
- *组内声明关联*：项目归属写在组侧的 =:configs=，加载期由插件物化成该项目对组的引用，界面 / 启停 / 导出五处读取点看到的是同一形态。
- *旧写法平滑迁移*：v0.1 的项目侧 =:groups= 仍然可用 —— 与组侧配置指向同一项目同一组时由配置 *原位接管*（不报错）；界面新建 / 改配置时若发现旧引用会问你是否顺手删掉，答 yes 才改写项目文件。
- *相对路径按项目 =:root= 解析*：派发时注入 =--project-directory=，顶层 =configs= / =secrets= 的 =file:= 、相对 =volumes= 源与 =env_file= 都以项目根为基准，而不是缓存目录。
- *服务级多选启停*：界面里勾选具体服务，批量执行启动 / 停止 / 重启，不强制整组起停。
- *状态轮询*：容器状态由 =docker ps --no-trunc= 采集并按标签归一，默认 3 秒轮询一次（见 =ebasecamp-status-refresh-interval=）。
- *导入已有 compose*：用 =docker compose config --no-interpolate= 系列 flag 读取项目 compose，映射为清单文件落盘（组内 =:configs= 写法）。
- *导出部署用 compose*：把项目的 per-project 组（含项目级覆盖）渲染为可直接部署的 compose 文件。
- *界面内编辑 container 配置*：按 =S= 打开服务编辑表单，改 =image= / =ports= / =environment= / =volumes= / =command= / =restart= 六个字段，只把你改动的字段写回清单，其余字段原样保留。
- *配置 / 项目 / 组的增删改*：=E= 改配置的关联项目、=M= 把配置移动到其他组的其他项目、=X= 打开清单操作菜单做配置 / 项目 / 组的 CRUD；删除带引用保护与影响提示。
- *密钥只存引用*：清单里只保存 =${VAR}= 引用与相对路径，插件不读取、不打印、不落盘任何密钥值。

* 安装

** 依赖

| 依赖 | 版本要求 |
|------+----------|
| Emacs | ≥ 29.1 |
| etaf | 0.2.3 |
| etaf-ui | 0.1.3 |
| Docker + Compose | Compose 5.x（本插件按 Compose 5.6.0 实测） |

** 方式一：straight.el（开发期，本地仓库）

开发插件本身时用 =:local-repo=，并显式声明 =:files= —— =ebasecamp.el= 在仓库根目录、实现模块在 =lisp/= 下，只拷 =.el= 会漏掉整个 =lisp/=：

#+begin_src elisp
(straight-use-package
 '(ebasecamp :type git
             :local-repo "/home/thomas/WorkSpace/ebasecamp"
             :files ("*.el" "lisp/*.el")))
#+end_src

改完代码要重建 build 目录（=M-x straight-rebuild-package RET ebasecamp=），否则运行中的 Emacs 仍在用旧副本 —— 现象是 =M-x ebasecamp= 报「命令不存在」（见「排查」一节）。

** 方式二：straight.el（发布后，远程仓库）

仓库发布后改成 =:repo=，=:files= 保持不变（=:repo= 的值替换成真实的用户/仓库名）：

#+begin_src elisp
(straight-use-package
 '(ebasecamp :type git
             :repo "OWNER/ebasecamp"
             :files ("*.el" "lisp/*.el")))
#+end_src

** 方式三：手工 load-path

#+begin_src elisp
(add-to-list 'load-path "~/WorkSpace/ebasecamp")
(add-to-list 'load-path "~/WorkSpace/ebasecamp/lisp")
(require 'ebasecamp)
#+end_src

=ebasecamp.el= 在仓库根目录，实现模块在 =lisp/= 下，两个路径都要加。

* 快速开始

1. 生成示例清单（=groups.el= 与 =projects/example.el=）：

   #+begin_src text
   M-x ebasecamp-create-sample-config
   #+end_src

   清单已存在时会报错拒绝覆盖；确实要覆盖时用 =C-u M-x ebasecamp-create-sample-config=。

2. 打开管理界面：

   #+begin_src text
   M-x ebasecamp
   #+end_src

界面分五区（以组为中心）：

- *顶栏*：=ebasecamp= 标题 + 统计（「N 组 · M 配置」）+ =刷新= 按钮；
- *左栏*：组树两级 —— 组节点（=MySQL  (1 配置 · 1/1 running)=）与配置节点（=host → 示例项目=）；未关联任何项目的组也照样出现在这里（=redis  (0 配置)=）；
- *右栏*：选中组的每份配置一段 =etaf-panel= —— 段头第一行 =配置名 → 项目名= + scope 徽标 + =running/total= 徽标，第二行 =启动选中= / =停止选中= / =重启选中= 三个按钮；段体是服务表（服务 / 镜像 / 状态 / 端口 / 健康，首列勾选框）；未选中组时显示「选择左侧的组」，选中组无配置时显示「尚未关联任何项目」并列出组定义的服务名（只读）；
- *底栏*：=导入 compose= / =导出 compose= / =销毁环境= 三个按钮；
- *提示区*：=etaf-alert= —— 成功 / 信息类 3 秒后自动消失，错误类保留到你手动关闭。

勾选流程：在右栏服务表里勾选目标服务 → 点该段（或该段所属项目）的按钮。点段内按钮只对 *该段自己的项目* 派发，同组多实例不会串段。勾选 key 是 =组名/服务名=（不含项目名与容器 ID），因此容器重启后选中仍稳定；同一组的两份配置里若服务同名，勾选状态 *跨段共享*（第一期语义）。=销毁环境= 会弹确认框，确认后只移除所选项目（per-project）的容器，不删卷。

* 清单怎么写

清单目录默认为 =ebasecamp-config-directory=（=~/.config/ebasecamp/=）；目录不存在时不会自动创建，加载结果里 =:bootstrap-needed= 为 =t=。

#+begin_src text
~/.config/ebasecamp/
├── groups.el        服务组定义（可选）
└── projects/*.el    项目定义，按文件名字典序加载
#+end_src

** 组定义放哪里：groups.el 或 projects/*.el

加载层按「=groups.el= （存在时）→ =projects/*.el= 字典序」读取全部清单文件，两类 form（=ebasecamp-define-group= / =ebasecamp-define-project= ）写在哪个文件里都能被读到 —— 所以 *组定义可以放在 =groups.el= ，也可以放在 =projects/*.el=* ，没有 =groups.el= 是完全正常的清单（导入功能就是把「组 + 项目」一起写进 =projects/<name>.el= 的）。

界面里的写操作（=S= / =E= / =M= / =X=）也不要求 =groups.el= 存在：它们 *按组名跨文件定位* 组定义的实际所在文件（=groups.el= 优先，其次 =projects/*.el= 字典序），改哪份配置就写回组真正所在的那个文件，不会凭空创建 =groups.el= 。

唯一硬约束是 *同一个组名只能在一个文件里定义*。同名组出现在多处时，加载层报错「组 X 已定义」，并且 *后加载的那个文件整体回滚* —— 与它同文件的项目定义一起消失，*该项目不会出现在界面中*（其余文件照常加载）。因此写操作一旦发现同一组名在多个文件中定义，会直接 *拒绝* 并列出这些文件，要求先清理重复定义，不会静默挑第一个。

** groups.el 示例

下面两个组覆盖了两种 scope、组内配置、服务字段与跨 scope 依赖，可整段粘贴到 =groups.el=：

#+begin_src elisp
;;; -*- lexical-binding: t; -*-

(ebasecamp-define-group mysql
  :title "MySQL"
  :scope shared
  :services
  ((mysql :image "mysql:8.4"
          :ports ((3306 . 3306))
          :volumes ((:source "mysql-data"
                     :target "/var/lib/mysql"
                     :type volume))
          :environment (("MYSQL_ROOT_PASSWORD"
                         . "${EBASECAMP_MYSQL_ROOT_PASSWORD}"))
          :healthcheck (:test ("CMD" "mysqladmin" "ping")
                        :interval "10s")
          :restart "unless-stopped"))
  :configs
  ((host :project example)))

(ebasecamp-define-group app
  :title "应用栈"
  :scope per-project
  :services
  ((api :image "example/api:latest"
        :ports ((8080 . 8000))
        :environment (("DATABASE_URL" . "${EBASECAMP_DATABASE_URL}"))
        :depends-on ("mysql")
        :volumes ((:source "../api"
                   :target "/app"
                   :type bind
                   :read-only t)))
   (redis :image "redis:7"))
  :configs
  ((dev :project example
        :services ((api :ports ((18080 . 8000))
                        :environment (("LOG_LEVEL" . "debug")))))))
#+end_src

读法：

- =mysql= 组是 =shared=，跨项目共用一套容器，只有 *一份* 配置（=host=）：shared 组的 =:project= 是「宿主」，只用于渲染上下文、=ebc-shared= 生成物命名与 =ebasecamp.project= 标签归属，不是业务绑定；
- =app= 组是 =per-project=，配置 =dev= 关联项目 =example=，可独立覆盖服务字段；
- =dev= 配置把 =api= 的宿主端口改成 18080 并加了 =LOG_LEVEL=；
- =depends-on ("mysql")= 指向 shared 组的服务，属于 *跨 scope 依赖*：=启动选中= 时会自动先把 shared 批次拉起来。

** projects/example.el 示例

#+begin_src elisp
;;; -*- lexical-binding: t; -*-

(ebasecamp-define-project example
  :title "示例项目"
  :root "~/Workspace/example"
  :shared-network t
  :export-file "deploy/compose.yaml")
#+end_src

项目文件里 *通常不写* =:groups= —— 项目对组的引用由组内 =:configs= 在加载期物化而来。旧写法仍然兼容（见「旧写法」一节）：项目侧 =:groups= 与组侧 *1 份* 配置指向同一项目同一组时，由组侧配置 *原位接管*、不报错；只有 *两份以上* 组侧配置指向同一项目同一组才报错。

项目定义里的 =:root= *现在是路径基准*，不只是「在项目中打开」时的定位依据：生成物里的相对路径（顶层 =configs= / =secrets= 的 =file:=、以 =.= 开头的 =volumes= 源、=env_file=）都按它解析，见「compose 生成物与路径基准」一节。

=:root= *是可选的*（v0.5.3 起写盘、界面、导出三处都已放开）：把整行删掉、或在界面里把根目录留空，就是一个「无根目录项目」。留空有 *三条后果*，界面与 =docs/user-guide.org= 都会提示：

- *不参与项目定位*：界面打开时不会因为你站在该项目目录里就自动选中它的配置（不知道目录，就不猜）；
- *不作路径基准*：派发不带 =--project-directory=，生成物里的相对路径退回「按缓存目录解析」；相对 =file:= 的预校验 *降级为警告*（成功提示末尾的「（N 条预校验警告）」），真正的缺失要到容器创建阶段才暴露；
- *导出必须显式选路径*：无 =:root= 也无 =:export-file= 时，交互式导出会弹 =read-file-name= 让你当场选；脚本 / batch 调用仍会报错（必须自己传 =:file=）。

反过来，*导入出来的项目通常自带 =:root=* —— 导入层取被导入 compose 文件所在目录作为项目根，恒非 nil。所以「无根目录项目」基本只出现在手写清单、从别处拷来的项目、或「只想把几个服务挂起来跑、暂不关心部署路径」的场景。也正因如此，*不要为了填空而写一个假路径*：它会成为派发基准，把相对路径解析到一个空目录里。

** 关键字表

组定义 =ebasecamp-define-group= 支持 =:title=、=:scope=、=:services=、=:configs=；=:scope= 取 =shared= 或 =per-project=，缺省 =per-project=。

项目定义 =ebasecamp-define-project= 支持 =:title=、=:root=（*可选*）、=:shared-network=、=:export-file=、=:groups=（旧写法）。=:shared-network= 缺省为 =t=，控制是否在生成物顶层把 =ebasecamp= 声明为 external network。

配置项写在 =:configs= 里，格式 =(配置名 :project 项目名 [:services 覆盖...])=：

| 规则 | 说明 |
|------+------|
| 配置名 | symbol，*组内唯一*；重复会加载报错 |
| =:project= | *必填*，symbol，必须指向已定义的项目（项目文件可后加载，存在性在物化阶段校验） |
| =:services= | 可选，格式 =((服务名 :字段 值 ...) ...)=，与旧写法的组引用覆盖格式一致 |
| =:scope= | *不允许*：配置的 scope 恒等于组定义的 scope |

服务定义支持 =:image=（必填）、=:command=、=:entrypoint=、=:environment=、=:labels=、=:ports=、=:volumes=、=:healthcheck=、=:depends-on=、=:networks=、=:working-dir=、=:user=、=:restart=、=:extra=。

未知关键字会报错（错误记入加载结果的 =:errors=，不中断其他文件）。

** 字段写法约定

- =:scope shared= 与 =:scope per-project= 的差异：shared 组渲染进 compose 项目 =ebc-shared=，跨项目共用同一套容器；per-project 组渲染进 =ebc-<project>=，每个项目各自一套。两组分别落在不同 compose 项目里，网络通过 external network =ebasecamp= 互通。
- =ports= 用 =(PUBLISHED . TARGET)= 整数对，例如 =(3306 . 3306)= 表示宿主 3306 → 容器 3306。
- =volumes= 用 plist：=(:source S :target T :type volume|bind [:read-only t])=。=:read-only= 非 nil 时挂载追加 =:ro=；命名卷在生成物里自动改成 =ebasecamp-<scope>-<组>-<source>=。
- =environment= 与 =labels= 是字符串 alist，值用 =${VAR}= 引用，插件原样保留不插值。
- =:extra= 存放清单未识别的 compose 字段，导出时原样回写；清单层不校验其键名。

** compose 顶层 =configs= / =secrets=

compose 允许服务引用顶层声明的 config / secret（服务级 =configs: [{source: web_cfg}] = 指向上面的顶层 =configs: {web_cfg: {file: ./web.conf}}= ）。导入时这两个顶层段会保留到 *项目定义* 的 =:file-configs= / =:file-secrets= 槽，per-project 生成物渲染时再输出回去：

#+begin_src elisp
(ebasecamp-define-project example
  :title "示例项目"
  :root "~/Workspace/example"
  :file-configs (("web_cfg" ("file" . "./web.conf")))
  :file-secrets (("db_pass" ("file" . "./db_pass.txt"))))
#+end_src

值的形态是 *compose 原样结构*（字符串键的 alist），插件只校验「键必须是字符串」而不做更深语义校验；清单里照旧只存相对路径与 =${VAR}= 引用。

四条边界：

- *老清单需要重新导入一次*：v0.5.1 之前导入的清单 *没有* =:file-configs= / =:file-secrets= —— 服务级 =configs:= 引用还在（走 =:extra= 原样透传），顶层段却已丢失，此时启动会报 =service "xxx" refers to undefined config=。修法是对 *原 compose 重新导入一次*（=M-x ebasecamp-import-file= 或界面底栏 =导入 compose= ），顶层段就补齐了；插件不会自动改写你的清单。
- *支持 =file:= / =external= / =name= 与 inline =content:= （含多行）*：顶层 config / secret 的值为「字符串键的 alist」。多行 =content:= 以 YAML 块标量保真往返（chomping 按末尾换行数取 =|-= / =|= / =|+= ），双引号标量转义换行与回车；=config -q= 只校验语法，判据须用 =config --format json= 对比内容（见 [[file:openspec/tech-debt.md][技术债]] #33，已关闭）。
- *shared 生成物不含顶层段*：=ebc-shared= 只渲染 shared 组服务，不带顶层 =configs: / secrets:= ；shared 组服务若引用顶层 config / secret，需要自行处理。
- *界面不编辑顶层段*：第一版只保证「导入 → 渲染往返不丢」，界面里没有编辑 =:file-configs= / =:file-secrets= 的入口，需要时手写清单（=e=）。

** compose 生成物与路径基准

生成物（per-project 为 =~/.cache/ebasecamp/<project>/compose.yaml= ，shared 为 =<cache>/_shared/compose.yaml=）是缓存目录里的派生产物，可随时重建。但 *清单里的相对路径不是相对生成物* ，而是 *相对项目的 =:root=* ：

| 清单里的相对路径 | 解析基准 |
|------------------+----------|
| 顶层 =configs:= / =secrets:= 的 =file:= | 项目 =:root= |
| =volumes:= 中以 =.= 开头的 =:source=（bind 挂载） | 项目 =:root= |
| =env_file:= 的路径 | 项目 =:root= |
| =compose.yaml= 自身所在位置 | =~/.cache/ebasecamp/<project>/=（只管生成物本身，不影响上面三项） |

实现方式是派发给 docker 时注入 *根级 flag* =--project-directory= ：

#+begin_src text
docker compose -f <cache>/<project>/compose.yaml --project-directory <root> -p <name> up -d …
#+end_src

它是根级 flag，必须在子命令 *之前*；预校验（=config -q=）与真正的 =up= / =stop= 用 *同一个* =root= —— 基准不同会重现「校验通过、启动炸」。

于是 *=:root= 现在承担实际语义*，不再只是「在项目中打开时定位用」：

- 项目写了 =:root= → 相对路径按它解析；
- 项目 *没写* =:root= → 不注入该 flag，退回「按生成物所在目录解析」（v0.5.1 及之前的行为）。此时顶层 =configs= / =secrets= 的相对 =file:= *无法校验*，预校验只给一条警告（见「启动前的 compose 预校验」），真正的失败会推迟到容器创建阶段；
- shared 生成物（=ebc-shared=）用 *触发本次操作的那个项目* 的 =:root= —— shared 配置的 =:project= 只是渲染上下文，不参与推导。因此同一份 =_shared/compose.yaml= 由不同项目触发时基准会不同，这正是「相对路径属于触发者」的语义。

*副作用（请知悉）*：注入 =--project-directory= 后 docker 会读取 =<root>/.env= （compose 的默认行为）。项目根目录里有 =.env= 时，其中的变量会参与生成物的变量解析 —— 这是 docker 的标准语义，插件既不读取也不改写该文件。

** 覆盖合并语义

覆盖写在配置的 =:services= 里，按服务名逐字段处理：=environment=、=labels=、=:extra= 按键合并（项目值覆盖同键、其余键保留），=image=、=command=、=entrypoint=、=ports=、=volumes=、=healthcheck=、=depends-on=、=networks=、=working-dir=、=user=、=restart= 整体替换。覆盖组内不存在的服务名会报错。

** 旧写法（项目侧 :groups，v0.1）

v0.1 的写法仍然可用，视作「匿名配置」（配置名等于组名），引用可带 =:scope= 与 =:services=：

#+begin_src elisp
(ebasecamp-define-project example
  :title "示例项目"
  :groups ((mysql)
           (app :services ((api :ports ((18080 . 8000)))))))
#+end_src

新旧写法可以共存。规则是 *同一项目同一组只允许 1 个有效引用*，但「谁说了算」取决于冲突形态：

| 形态 | 结果 |
|------+------|
| 项目侧 =:groups= 引用某组，同时组侧 *1 份* =:configs= 配置指向同一项目同一组 | *以组侧配置为准*：加载时旧引用被 *原位接管*（列表位置不变，=:scope= 与 =:services= 取配置值），*不报错* |
| *两份以上* 组侧配置指向同一项目同一组 | 报 =ebasecamp-config-duplicate-group-ref=，消息里点名第一份配置 |
| 同一项目在 =:groups= 里重复引用同一组 | 报错（v0.1 是静默取首个） |

「原位接管」意味着老清单 *不必* 立刻手工清理：项目文件里的 =:groups= 仍指向该组，但界面、启停、导出读到的都是配置形态（段头有配置名、覆盖按配置生效）。不过两处写法长期并存容易混淆，因此界面里 *新建配置* / *=E= 改配置关联项目* 时若检测到同一项目同一组的旧 =:groups= 引用，会弹一句确认：

#+begin_src text
项目 example 的旧写法 :groups 仍引用组 redis；新建配置后该旧引用将被组侧配置
接管。是否同时删掉这条旧引用？
#+end_src

- 答 yes → 在 *同一批写盘事务* 里删掉项目文件里的那条旧引用；若它是 =:groups= 里唯一元素，整个 =:groups= 键一并移除（不会留下 =:groups nil=）；
- 答 no → 写盘照常成功（由上面的「原位接管」兜住），下次新建 / 改配置还会再问一次。

插件 *绝不* 在未经确认的情况下改写你的项目文件：写盘层的迁移开关默认关闭，只有你在确认框里答 yes 才打开。=M=（移动配置）*不做* 迁移 —— 跨组移动不产生新的「同项目同组」关联，撞到旧写法同样由接管兼容。

* 界面键位

界面 buffer =*ebasecamp*= 是只读的：它只是清单的投影，在界面里敲的字不会落到任何文件。改配置有两条路：按 =S= / =E= / =M= / =X= 走界面表单（改动由插件写回清单），或按 =e= 打开该组定义所在的清单文件（=groups.el= 或 =projects/*.el= ）手写 Elisp。两条路共用同一个写盘事务内核（备份 → 原子写 → 校验 → 失败回滚），所以表单与手工编辑的安全性一致。写完全局生效，界面自动重载；界面内按 =?= 弹出全部键位；其余字母在界面内无反应，例如 =i= 不会进入 evil 的 insert state。

*按钮上的方括号提示*：底栏的 =[I] 导入 compose= / =[o] 导出 compose= / =[D] 销毁环境= 与段头的 =[s] 启动选中= / =[x] 停止选中= / =[r] 重启选中= 里的键名就是按下即生效的键。提示文案与 =?= 帮助 *同源*：键位的唯一事实源是根级与段级两张键表，按钮只在渲染时把键名前置成 =[KEY] LABEL= ，所以帮助页与按钮不会各自漂移。

** 界面布局

界面是「顶栏 / 中间两栏 / 底栏」三段式，总高恒等于窗口高：

- *底栏常驻窗口底部*：=导入 compose= / =导出 compose= / =销毁环境= 三个入口与提示区固定在底部，不再排在树之后 —— 不需要先把整窗滚到底才能看到它们。
- *左树与右栏各自内部滚动*：配置多时只有当前区域的列在滚，顶栏与底栏不动，整窗不再滚动。滚轮按「最内层可滚区域优先」分派，所以左栏只滚左栏、右栏只滚右栏。
- *左栏宽度可拖动*：分隔线可用鼠标拖动（也支持键盘拖动），宽度钳制在 *0.15–0.55* 之间；默认 0.26（约占窗口宽度 26%），把宽度让给右栏的服务表格。
- *宽度跨会话记住*：拖动结果写在 =~/.cache/ebasecamp/ui-state.el=（运行时状态缓存，*不是清单*，不参与 =ebasecamp-config-load=，可随时删除，下次打开回默认）。

** 启动前的 compose 预校验

=s= （与段头 =启动选中= 、=r= / =重启选中= ）在派发 =docker compose up= 之前先对生成物做一次 *compose 预校验*（=config -q= ，退出码 + stderr 双判据）：

- 本次要启动 shared 与 per-project 两类生成物时 *逐个校验*，全部通过才进入启动，不会出现「已启动一部分」的中间态；
- 只要有生成物不合法就 *一个容器都不启动*，连 external network =ebasecamp= 都不创建（零副作用），并在提示区显示 stderr 首行这类可读错误，例如 =service "api" refers to undefined config web_cfg: invalid compose project= —— 不再是笼统的 =invalid compose project= ；
- *顶层 =configs= / =secrets= 的 =file:= 存在性单独检查*：=config -q= 只校验 =env_file= ，*不校验*顶层 config / secret 的 =file:= （缺文件要到容器创建阶段才以 =bind source path does not exist= 暴露）。因此 v0.5.2 在 =config -q= 之前由插件自己按 *项目 =:root=* 逐条检查 =file:= ：相对路径拼 =<root>/<file>= 后判存在性，绝对路径直接判；没有 =file:= 的条目（=external: true= / 纯 =name:=）跳过。任一条缺失就 *中止并给出可读错误*，一个生成物都不写、一个 docker 进程都不派发：

  #+begin_src text
  顶层 config `app_cfg' 的 file `./conf/app.conf' 不存在（基准：/home/me/proj/conf/app.conf）
  #+end_src

- 项目 *没有* =:root= 而有相对 =file:= 时无法判定 → *只给警告、不阻塞启动*，成功提示末尾会追加「（N 条预校验警告）」；
- =x= （停止）与 =D= （销毁）*不做*预校验：它们作用于已经存在的容器，生成物暂时不合法时更应该允许先把服务停掉。

** 关于 =SPC=

=SPC= 与 =RET= 等价，都是「激活当前控件」：在勾选框上勾选、在按钮上按下。它 *不是* 本插件的勾选键，也不能在界面 buffer 里当 general 或 evil 的 leader 前缀用。行级切换勾选请用 =t= 键，它不会误触按钮。

** 编辑清单的流程

想直接改 Elisp（表单覆盖不到的字段、块间注释、组服务定义本身）：

1. 按 =e= 打开该组定义所在的清单文件（=groups.el= 或 =projects/*.el= ），point 停在当前组的 =(ebasecamp-define-group= 那行；
2. 改完保存；
3. 回界面按 =g= 重载清单并刷新。

只想改端口 / 环境变量 / 卷 / 命令 / 重启策略 / 镜像的话，用 =S= 表单更快，也省得自己对齐缩进。

** 编辑 container 配置

把 point 放到右栏某个服务行上，按 =S= 打开服务编辑表单。表单预填该服务的当前值，改完点 =保存= 写回清单；点 =取消= 丢弃。

可编辑的 6 个字段与书写规则：

| 字段 | 表单控件 | 书写规则 |
|------+----------+----------|
| =image= | 单行文本框（必填） | 镜像名，如 =mysql:8.4= ；留空会报错 |
| =ports= | 多行文本框 | *每行一项*：=HOST:CONTAINER=（如 =3307:3306=）或只写容器端口 =CONTAINER=（如 =80=）；两段都必须是十进制整数 |
| =environment= | 多行文本框 | *每行一项* =KEY=VALUE= ，按 *首个* = = 切分值（值里可以再有 = = ）；同一字段内键不可重复；=${VAR}= 原样保留、不插值 |
| =volumes= | 多行文本框 | *每行一项* =SRC:DST[:ro]= ；源以 =.= 或 =/= 开头视为 bind 挂载，否则视为命名卷；只写 =DST= 表示匿名卷；第三段只能是 =ro= ，写成 =rw= 会报错（要可写就不写第三段） |
| =command= | 多行文本框 | exec 形式，*每行一个参数*；参数自身含空格时必须用多行（单行输入会按空白切分，等于无法表达带空格的单个参数） |
| =restart= | 下拉选择 | =no= / =always= / =on-failure= / =unless-stopped= 四选一，或选「自定义…」手输 =on-failure:5= 这类自由值；原值不在这四个里时下拉自动落到「自定义」并显示原值 |

保存语义：

- *只提交改动字段*：打开时快照一份原值，保存时逐字段比对，只有真正改过的字段才写进清单；没碰的字段连重写都不做（清单里那几个键逐字节不变）。
- *清空字段 = 删除该键*，不是写空串。例如把 =ports= 的多行框清空，写回后该服务就没有 =:ports= 了。
- *表单之外的字段原样保留*：=healthcheck= / =labels= / =networks= / =depends-on= / =entrypoint= / =working-dir= / =user= / =extra= 不在表单里，写回时从清单 *原文* 取值带回（不经模型归一化），因此 =command= / =entrypoint= 原先是字符串（shell 形式）就仍是字符串。
- *校验在写盘之前*：非法端口、缺 = = 的环境变量行、缺冒号的卷、空的 =image= 都会在表单内以 *行号* 报错，表单 *不关闭*；此时磁盘上没有任何改动，修好再保存即可。

** 配置与项目、组操作

除服务字段外，配置、项目、组本身也能在界面里增删改：

| 键 | 动作 | 说明 |
|----+------+------|
| =E= | 改配置的关联项目 | 选一份配置（组内只有一份时不问），再用 =completing-read= 选目标项目，写回 =:configs= 里该配置的 =:project= |
| =M= | 移动配置到其他组的其他项目 | 两级选择：目标组 → 目标项目；写盘在 *一次事务* 内完成「源组移除 + 目标组追加」，中间不会有半成品状态；配置自带的 =:services= 覆盖随配置一起搬走 |
| =X= | 清单操作菜单 | 一个 =completing-read= 里 8 项：新建配置 / 删除配置 / 新建项目 / 改项目 / 删除项目 / 新建组 / 改组 / 删除组 |

=X= 菜单里删除类操作都有两道防线：

- *引用保护*：删 *项目* 前扫所有组的 =:configs= ，只要有配置指向该项目就拒绝，并列出「组/配置」清单（如 =alpha/dev=）；删 *组* 前扫所有 =projects/*.el= 里 v0.1 旧写法的 =:groups= ，有项目引用就拒绝并列出项目名。拒绝时磁盘不动。
- *影响提示*：确认框写明「只删清单定义，容器需用 =D= 销毁」。删组 / 删项目 *只删清单*（组 form 或项目文件），已经在跑的容器不会被自动清理；要清理容器请用 =D= （只覆盖 per-project 项目）或 =docker rm -f=。

新建与修改类的约束：配置名 *组内唯一* 且 *同一项目同一组只允许 1 份配置*（冲突会被拒绝并说明来源配置）；项目名与组名只允许 =[a-z0-9_-]+= ；新增项目时如果 =projects/<name>.el= 已存在会被拒绝（改项目请用「改项目」）；组 scope 只能是 =shared= 或 =per-project= 。

所有写操作都走同一个 *事务*：备份原文 → 同目录临时文件 + =rename-file= 原子写 → 重新加载清单校验 → 失败自动回滚并给出行号；成功则删除备份。写前还会比对文件的 mtime 与大小，如果你在外部改过这个文件，写入会被 *拒绝* 并提示先按 =g= 重载清单，避免覆盖掉你的改动。

写操作的 *目标文件按组名跨文件定位*：组定义在 =groups.el= 或任意 =projects/*.el= 都能被找到（=groups.el= 优先，其次 =projects/*.el= 字典序），「没有 =groups.el=" 不再导致写盘失败；同名组在多处定义时写操作拒绝执行并列出文件（同名组在加载层就是硬错误，见「清单怎么写」一节）。=M= 跨文件移动一份配置时是 *两次事务 + 备份补偿*：第一段从源文件移除、第二段写入目标文件，第二段失败就用第一段的备份把源文件恢复原文，两段都成功才删备份。

** 主题

界面颜色不写死，跟着 Emacs 主题走：

- *跟随主题*：基础色（前景 / 背景 / 面板 / 边框）从当前 face 取（=default=、=mode-line-inactive= 等），状态色（success / warning / danger / info / 按钮 / 徽标 / 勾选框）按当前明暗（=background-mode=）从内置的明暗两套 palette 取。
- *切换即时生效*：=M-x load-theme= 之后界面立即变色，不需要重开界面或重载清单 —— 主题变化只刷新节点属性，不重建整棵树。暗色主题下的徽标与提示块不会再是浅色块。
- *自定义覆盖*：=ebasecamp-ui-theme=（默认 =nil=，表示完全跟随）可以按 token 覆盖，未覆盖的键仍按「face → 内置 palette」生成：

  #+begin_src elisp
  (setq ebasecamp-ui-theme '(:ui-accent "#B45309"
                             :ui-accent-soft-bg "#FDF2E3"))
  #+end_src

  一共 35 个 =:ui-*= token（9 个基础色 + 26 个状态色）；界面没用到的 etaf-ui token（shell / window / search / picker 等）继续走 etaf-ui 的默认 palette。

** 在项目中打开

- *自动定位*：在某个项目目录里（=default-directory= 落在该项目 =:root= 之下）执行 =M-x ebasecamp= ，打开时会自动选中 *该项目第一份配置所属的组*。
- *「第一份」的定义*：按 =groups.el= 的组定义顺序、组内 =:configs= 顺序，首个 =:project= 命中该项目的配置。
- *最长 root 胜出*：=:root= 嵌套时（=/a= 与 =/a/deep=）取更长的那个；路径比较前用 =file-truename= 归一，因此 =~=、=..=、软链不影响判断；比较 *大小写敏感*，只匹配整段目录（=/tmp/a2= 不会被 =/tmp/a= 命中）。
- *无匹配则不选中*：当前目录不在任何项目 =:root= 之下，或该项目还没有配置时，*不选中任何组*，右栏保持「选择左侧的组」。
- *只在打开时算一次*：=g= 与 =M-x ebasecamp-ui-refresh= 不会覆盖你手选的组；关闭界面再打开才重新定位。

* 安全约束

- 清单只保存 =${VAR}= 引用与相对路径，不落盘密钥明文；
- 读取项目 compose 只用 =docker compose config --no-interpolate --no-env-resolution --no-path-resolution --format json=，三个 flag 缺一不可：分别避免密钥明文展开、=env_file= 内容被合并、相对路径被绝对化；
- 生成物（=~/.cache/ebasecamp/<project>/compose.yaml=）中同样只有 =${VAR}= 引用，不含明文；
- 校验用 =config -q=，并且同时检查退出码与 stderr（退出码 0 不足以判定通过）。

* 已知限制

- 按 Compose 5.x 实测（本机 5.6.0），其他主版本的 =--format json= 键集可能不同；插件有 =docker compose version= 检测，不匹配时会告警。
- 同一项目同一组只能 1 份配置：容器标签没有配置维度，同名服务会撞。
- shared 组至多 1 份配置且 =:project= 必填：多宿主会互相覆盖 =_shared/compose.yaml= 与 =ebc-shared= 容器集合。
- D4 之前导入的清单需重新导入：=env_file= 的清单形态已由 =((:source PATH :type env))= 改为路径字符串列表（=("./db.env")=）。
- shared 组没有插件侧清理入口：=销毁环境= 只覆盖 per-project，shared 容器需 =docker rm -f=。
- 容器状态是 3 秒轮询（仅界面可见时），状态最多滞后一个轮询周期；需要即时值点 =刷新=。
- 自定义网络的 external 语义无法表达；跨组同名服务在 compose 生成时静默保留首个，不报错。
- =:extra= 字段原样透传，清单层不做 schema 校验，写错字段会导致 =config -q= 失败。
- 不做清单与项目 compose 的双向同步；导入是单向的，导出也是单向的。
- =重启选中= 不补齐 shared 依赖分支（=启动选中= 才会自动先起 shared 批次）；=depends-on= 里的笔误也会被静默剔除。
- 服务 *增删与改名* 仍不支持：增删会让既有容器变孤儿，改名要迁移容器标签与命名，需先有配置维度（见 =openspec/tech-debt.md= #16 / #25 / 新增条目）。服务字段编辑、配置 / 项目 / 组的增删改已支持。
- 端口冲突只在 =启动选中= 前检测；=unknown= 类探测失败只提示、不阻塞。
- 组名与项目名只允许 =[a-z0-9_-]+=，其余字符在渲染时直接报错。
- 顶层 =configs= / =secrets= 的 inline =content:= （含多行字符串）已支持：多行值以 YAML 块标量保真往返（chomping 按末尾换行数取 =|-= / =|= / =|+= ），=file:= / =external= / =name= 形态行为不变。判据须用 =config --format json= 对比 =content= 字符串，因为 =config -q= 只校验语法不校验内容。
- shared 生成物（=ebc-shared=）不输出顶层 =configs= / =secrets= ：shared 组服务引用顶层 config / secret 时需自行处理。
- v0.5.1 之前导入的清单缺 =:file-configs= / =:file-secrets= ：引用顶层 config 的服务启动会报 =refers to undefined config= ，需对原 compose *重新导入一次* 补齐（插件不自动改清单）。
- 同一组名在多处定义是加载层硬错误：后加载的文件会 *整体回滚* ，其中项目不会出现在界面中；界面写操作遇到同名组直接拒绝。
- 导出到 *项目 =:root= 之外* 的目录时，顶层 =configs.file= 的相对路径仍会失效（导出物的路径基准由导出目标位置决定，插件不做改写）。
- 相对 =volumes= 源（以 =.= 开头的 bind 挂载）*没有* 存在性检查：预校验只覆盖顶层 =configs= / =secrets= 的 =file:= ，volume 源缺失要到容器创建阶段才报 =bind source path does not exist= 。
- =M=（移动配置）*不做* 旧 =:groups= 引用迁移：它不产生新的「同项目同组」关联，若目标项目仍用旧写法引用该组，由「原位接管」兼容（要清理旧引用请用 =X= 新建配置，或答 yes 的确认提示）。
- 项目没写 =:root= 时的相对路径无法校验：预校验只给「（N 条预校验警告）」；顶层 =configs= / =secrets= 的 =file:= 与相对 =volumes= 源要到容器创建阶段才报 =bind source path does not exist= （=env_file= 例外 —— =config -q= 会校验它，此时基准是生成物所在的缓存目录）。

* 排查：=M-x ebasecamp= 提示命令不存在

最常见的原因是包没装进当前 Emacs，或 straight 装的是旧副本（改了代码没重建 build 目录），第三是 daemon 启动早于 build 完成。最小自查（在 *当前这个 Emacs* 里逐个求值）：

#+begin_src elisp
(locate-library "ebasecamp")   ; 期望指向仓库或 straight build 目录，nil 表示根本没装
(fboundp 'ebasecamp)           ; 期望 t，nil 表示命令不存在
#+end_src

两条都对而 =M-x ebasecamp= 仍不可用 → 问题在安装而不是代码；=locate-library= 指的路径与你改的仓库不一致 → 是旧副本，重建后重启 Emacs。

完整排查（三条原因的判别命令、straight 产物检查、stale =.elc= 陷阱、修法）见 [[file:docs/troubleshooting.org][排障手册]] 第 1 条「=M-x ebasecamp= 报命令不存在」。

* 开发

所有验证走 =emacs -Q --batch=，不加载用户 init：

| 命令 | 作用 |
|------+------|
| =make check= | 串联执行下面三个子目标，任一失败即非零退出（提交前必跑）。 |
| =make check-parens= | 对 =*.el=、=lisp/*.el= 与 =test/*.el= 逐个做括号平衡检查。 |
| =make compile= | 字节编译，启用 =byte-compile-error-on-warn=，零 warning 才算通过。 |
| =make test= | 用 ERT 运行 =test/*-tests.el=。 |
| =make clean= | 删除与 =.el= 同名的 =.elc=。 |

=ELPA_LOAD_PATH= 指向 straight 的 build 目录，使 batch 模式下能 =require= etaf 系列包（=etaf=、=etaf-ui=、=ebox=、=ecss=）。换 Emacs 版本或路径时用变量覆盖：

#+begin_src text
make check EMACS=/path/to/emacs STRAIGHT_BUILD=/path/to/build-XX.X
#+end_src

修改 =Makefile= 后至少跑一次 =make check=。batch 脚本里要读最新源码，首行加 =(setq load-prefer-newer t)=（防 stale =.elc=）。
